# 감사 로그 포맷 규격 (airlock.audit.v2)

`airlock-audit`이 구현하는 append-only 해시체인 로그의 규격입니다. 구현과 이 문서가 어긋나면 이 문서가 정본입니다.

이 문서는 포맷 **v2**를 규정합니다. v1으로 기록된 체인은 마이그레이션하지 않고 거부합니다. 근거는 7.1절에 있습니다.

## 1. 목표와 비목표

### 목표

- 브로커가 관측한 모든 중재 지점을 순서와 함께 기록합니다.
- 엔트리 하나를 고치거나 지우거나 끼워 넣으면 그 지점부터 체인이 깨집니다.
- 어떤 정책이 적용된 상태였는지 로그 자체로 증명합니다.
- 검증자가 **옛 포맷**과 **위조**를 구분할 수 있습니다. 두 사유가 같은 실패로 보고되면 진짜 변조가 포맷 변경 소음에 묻힙니다.
- 세션을 통째로 지우거나 체인을 처음부터 다시 계산한 흔적을 세션 바깥의 앵커 체인으로 남깁니다.
- 사람과 도구가 같이 읽을 수 있습니다.

### 비목표 (v2)

- 파일시스템 전체에 쓰기 권한을 가진 공격자로부터의 보호. 해시체인은 체인 전체를 다시 계산할 수 있는 공격자를 막지 못하므로 2절을 참고합니다.
- v1 체인의 자동 변환. 감사 로그를 조용히 다시 쓰는 것은 증거 파기와 구분되지 않습니다 (7.1).
- 실시간 원격 전송, 로그 회전, 압축

## 2. 이 포맷이 실제로 보장하는 것

해시체인만으로 "위조 불가능"이라고 말하면 거짓입니다. 정확한 경계는 다음과 같습니다.

| 공격자 능력                          | v2 결과                             |
|---------------------------------|-----------------------------------|
| 로그 디렉토리에 쓰기 권한 없음 (샌드박스된 에이전트)  | 변조 불가, 강제 층이 실제 보장을 제공            |
| 엔트리 일부만 수정/삭제/삽입                | 검증에서 반드시 탐지                       |
| 로그 파일 뒤쪽만 잘라냄 (`head.json`은 그대로) | `head.json`과 대조해 탐지               |
| 뒤쪽을 자르고 `head.json`도 함께 고쳐 씀     | 세션 디렉토리만으로는 탐지 불가, 앵커 체인이 있으면 탐지  |
| 체인 전체를 처음부터 재계산해 교체             | 세션 디렉토리만으로는 탐지 불가, 앵커 체인이 있으면 탐지  |
| 세션 디렉토리를 통째로 삭제                 | 앵커 체인이 있으면 탐지, 없으면 탐지 불가          |
| 앵커 파일까지 같은 권한으로 다시 계산           | 탐지 불가. 하드웨어 서명이 로드맵에 있는 이유        |
| 옛 포맷(v1)으로 기록된 체인               | 변조가 아니라 포맷 불일치로 구분해 보고 (7.1)      |

`head.json`은 `chain.jsonl`과 같은 디렉토리에 같은 권한으로 있습니다. 곧 체인을 자를 수 있는 공격자는 `head.json`도 고칠 수 있으므로, `head.json`은 "쓰기 권한이 체인에만 있고 앵커에는 없는" 공격자만 막습니다. 실제 파일시스템 권한 모델에서 그런 분리는 생기지 않습니다. `head.json`의 값은 부분 쓰기나 크래시로 끊긴 파일을 탐지하는 데 있지, 권한을 가진 공격자를 막는 데 있지 않습니다.

8절의 세션 상위 앵커 체인도 **같은 디렉토리 트리 안에 두면 같은 이유로 무력합니다.** 앵커에 실질 탐지력이 생기는 것은 그 파일을 **다른 볼륨이나 원격 마운트로 분리해, 세션 디렉토리에 쓸 수 있는 주체가 앵커에는 쓸 수 없을 때뿐**입니다. 이 문서는 앵커를 자동으로 어딘가에 복제하지 않으며, 분리는 운영자의 배치 결정입니다. 분리하지 않은 앵커는 크래시와 부분 쓰기 탐지용이라고만 말해야 합니다.

곧 실제 강제력은 두 가지 조합에서 나옵니다. 첫째로 감사 디렉토리를 강제 층이 에이전트에게 쓰기 금지하고, 둘째로 해시체인이 그 방어가 뚫렸을 때 흔적을 남깁니다. 전자 없이 후자만으로는 부족하다는 사실을 제품이 숨기지 않습니다.

## 3. 저장 레이아웃

감사(audit) 세션 하나는 디렉토리 하나입니다. 앵커 체인은 세션 디렉토리 **바깥**에 하나만 있습니다.

```
<audit-root>/
  anchors.jsonl          세션 상위 앵커 체인. 세션마다 한 줄 (8절)
  reviews.jsonl          책임자 확인 체인. 점검마다 한 줄 (9절)
  sessions/
    <session-dir>/
      chain.jsonl        엔트리 로그, 한 줄에 JSON 오브젝트 하나
      head.json          세션 안 앵커. 마지막 seq와 해시
```

- `chain.jsonl`과 `anchors.jsonl`과 `reviews.jsonl`은 `O_APPEND`로만 엽니다. 기존 바이트를 덮어쓰는 경로는 구현에 존재하지 않습니다.
- 디렉토리 권한은 `0700`, 파일 권한은 `0600`으로 생성합니다. 앵커 파일과 확인 파일도 같습니다.
- 앵커 파일과 확인 파일은 최종 구성 요소를 `O_NOFOLLOW`로 엽니다. 미리 놓인 심볼릭 링크로 그 파일을 다른 곳에 쓰게 만들 수 없어야 합니다.
- 강제 층은 이 디렉토리를 피보호 프로세스에 대해 쓰기 금지로 설정해야 합니다.
- 앵커 루트는 세션 루트와 다른 볼륨을 가리킬 수 있습니다. 2절이 밝히듯 앵커의 값은 그 분리에서만 나옵니다.

## 4. 쓰기 순서 (write-ahead)

결정을 기록한 다음에 행위를 허용합니다. 순서를 뒤집으면 허용된 행위가 로그에 없는 창이 생깁니다.

1. 정책을 평가해 결정을 얻습니다.
2. 엔트리를 `chain.jsonl`에 append하고 `fsync`합니다.
3. `head.json`을 갱신하고 `fsync`합니다.
4. 그다음에 비로소 행위를 허용하거나 거부합니다.
5. 세션이 끝나면 그 세션의 최종 head를 `anchors.jsonl`에 append하고 `fsync`합니다.

`ask` 결정은 사람이 답하기 전에 기록합니다. 승인 결과는 원래 엔트리를 고치는 것이 아니라 그 seq를 참조하는 별도 `approval` 엔트리로 append하며, 엔트리는 한번 쓰이면 불변(immutable)입니다. 이 규칙 덕분에 사용자가 답하지 않고 세션이 죽어도 시도 자체는 남습니다.

5단계는 세션 종료 경로에서만 일어납니다. 세션이 SIGKILL로 죽으면 그 세션의 앵커 줄은 생기지 않으며, 검증자는 그 상태를 "앵커 없음"으로 보고할 뿐 통과로 처리하지 않습니다.

`fsync`는 엔트리마다 수행합니다. 감사 로그에서 배치 플러시는 크래시 시 구간 손실을 뜻하므로 기본값이 될 수 없습니다. 성능이 필요하면 명시적 옵션으로 열되, 그 사실을 세션 시작 엔트리에 기록합니다. 앵커 append는 세션당 한 번뿐이므로 이 옵션과 무관하게 항상 `fsync`합니다.

## 5. 엔트리 스키마

`chain.jsonl`의 각 줄은 아래 필드를 갖는 JSON 오브젝트입니다. 필드 순서는 가독성을 위한 관례이며 해시에는 영향이 없습니다(6절의 정규 인코딩이 순서를 고정합니다).

| 필드            | 타입             | 설명                                           |
|---------------|----------------|----------------------------------------------|
| `v`           | u32            | 포맷 버전. v2에서 항상 `2`. 없으면 `1`로 해석 (5.2)        |
| `seq`         | u64            | 0부터 1씩 증가. 빈틈이 있으면 검증 실패                     |
| `ts`          | u64            | UTC 유닉스 시각, 나노초                              |
| `ts_rfc3339`  | string         | 사람이 읽는 표현. 해시 대상이 아니며 검증하지 않음                |
| `session`     | string         | 세션 식별자, 16바이트 랜덤의 소문자 hex                    |
| `actor`       | string         | 관측된 주체. 예 `pid:41233 claude`                 |
| `enforcement` | string         | `observe` \| `seatbelt` \| `landlock`        |
| `event`       | object         | 6.3의 태그된 유니온                                 |
| `decision`    | string         | `allow` \| `deny` \| `ask` \| `forbid`       |
| `rule`        | string \| null | 결정을 낸 규칙 id. 기본값 적용 시 null                   |
| `prev`        | string         | 이전 엔트리 해시의 소문자 hex 64자. 제네시스(genesis)는 0 64자 |
| `hash`        | string         | 이 엔트리 해시의 소문자 hex 64자                        |

`ts_rfc3339`이 해시 대상이 아닌 이유는 시각 렌더링 규칙이 바뀌어도 과거 체인이 깨지지 않게 하기 위함입니다. 권위 있는 값은 언제나 `ts`입니다.

### 5.1 제네시스 엔트리

`seq = 0`은 반드시 `session_start` 이벤트이고 `prev`는 0 64자입니다. 이 엔트리가 정책 다이제스트를 담으므로 체인 전체가 특정 정책 내용에 묶이며, 곧 "그 시점에 어떤 정책이 걸려 있었는가"를 로그만으로 증명할 수 있습니다.

제네시스는 관측 범위를 결정하는 두 값을 함께 담습니다.

- `argv`는 브로커를 띄운 실제 호출을 재구성할 수 있어야 합니다. 승인 통제를 포기하는 `--yes`처럼 결정의 의미를 바꾸는 플래그가 빠지면, 로그만 보고 그 세션의 승인이 사람 판단이었는지 자동이었는지 알 수 없습니다.
- `mediation`은 자식 프로세스의 syscall을 어디까지 브로커로 중계했는지입니다. **요청값이 아니라 그 플랫폼에서 실제로 적용된 값**을 기록합니다. 이 값이 없으면 `exec` 엔트리가 없는 체인이 "아무 일도 없었음"인지 "중계가 꺼져 있어 보이지 않았음"인지 구분되지 않습니다.

`enforcement`가 강제 층의 등급을 엔트리마다 밝히는 것과 같은 이유로 중계 수준도 로그에 남습니다. 강제되지 않은 기록이 강제된 기록처럼 보이지 않아야 한다는 원칙([`docs/design.md` 9.3](./design.md#93-강제-층-enforcer-트레이트-추상화-백엔드는-점진-도입))은 관측 층에도 그대로 적용됩니다.

제네시스는 주체 식별에 쓰이는 네 값을 더 담습니다.

- `uid`와 `euid`는 **감사 층이 `getuid(2)`·`geteuid(2)`로 직접 읽습니다.** 호출자가 넘길 수 없습니다. 넘길 수 있게 하면 로그가 관측이 아니라 주장을 담게 되고, 자기 자신을 다른 계정으로 기록하는 세션을 막을 방법이 없습니다.
- `operator`는 사람 식별자를 담는 자리입니다. 계정 uid가 아니라 "누가 이 실행에 책임을 지는가"를 가리키며, 지금 구현은 항상 `null`입니다.
- `policy_signer`는 중앙에서 배포된 정책의 서명자를 담는 자리입니다. 지금 구현은 항상 `null`이며, 정책 서명 검증이 들어오기 전에는 채우지 않습니다.

두 자리를 지금 비워 두더라도 인코딩 위치를 미리 확정해 둡니다. 나중에 필드를 끼워 넣으면 그 시점의 모든 과거 체인이 다시 깨지고, 그 깨짐은 위조와 구분되지 않습니다(7.1).

### 5.2 `v` 필드와 in-band 버전 신호

`v`는 정규 인코딩에서 **도메인 바로 다음, `seq`보다 앞**에 들어갑니다. 곧 버전 자체가 해시에 묶입니다. 이유는 하나입니다. 버전이 해시 밖에 있으면 위조자가 버전만 낮춰 검증자에게 옛 규칙을 적용시키고, 그 옛 규칙 아래에서 정합적인 체인을 내놓을 수 있습니다. 버전이 해시 안에 있으면 버전을 바꾸는 순간 그 줄의 해시가 함께 바뀝니다.

JSON 표현에서 `v`가 없는 줄은 `1`로 해석합니다. 이것은 v1 줄을 **받아들이기 위한 것이 아니라 정확히 거부하기 위한 것**입니다. `deny_unknown_fields`를 유지한 채 `v`만 기본값을 주면, v1 줄은 "필드 누락"이라는 파싱 오류가 아니라 "포맷 v1"이라는 사실로 파싱되고, 검증자는 `MalformedLine`이 아니라 `FormatVersionUnsupported`를 낼 수 있습니다. 이것이 v1에서 v2로 올린 이유의 전부입니다.

도메인 상수도 `airlock.audit.v2\x00`로 함께 올립니다. 버전 신호를 한 곳에만 두면 그 한 곳이 곧 단일 실패 지점이 됩니다. 도메인이 다르면 v1 검증자가 계산한 바이트열과 v2 바이트열은 **어떤 필드 조합으로도 일치하지 않습니다.**

## 6. 정규 인코딩

해시 입력은 JSON 텍스트가 아닙니다. JSON은 공백, 키 순서, 유니코드 이스케이프, 수 표기가 모두 비유일하므로 해시 입력으로 부적합하며, 대신 아래 길이 접두 이진 인코딩을 씁니다.

모든 가변 길이 필드에 길이 접두를 붙이는 이유는 연결 모호성을 없애기 위함입니다. 접두가 없으면 `("ab", "c")`와 `("a", "bc")`가 같은 바이트열이 되어 서로 다른 엔트리가 같은 해시를 갖습니다.

### 6.1 기본 요소

```
DOMAIN   = "airlock.audit.v2\x00"        도메인 분리 접두사
u64(n)   = n을 리틀엔디안 8바이트로
u32(n)   = n을 리틀엔디안 4바이트로
tag(n)   = n을 1바이트로
bytes(b) = u64(len(b)) || b
str(s)   = bytes(utf8(s))                정규화하지 않고 저장된 바이트 그대로
opt(x)   = tag(0)                        x가 없을 때
         = tag(1) || enc(x)              x가 있을 때
list(xs) = u64(len(xs)) || enc(xs[0]) || enc(xs[1]) || ...
```

문자열을 유니코드 정규화하지 않는 것은 의도된 것입니다. 경로 정규화는 정책 층의 책임이고([`docs/policy-dsl.md` 4절](./policy-dsl.md#4-경로-정규화)), 감사 로그는 관측된 바이트를 그대로 보존해야 합니다. 감사 층이 문자열을 손보면 원본 증거가 사라집니다.

### 6.2 엔트리 해시

```
hash = SHA-256(
    DOMAIN
 || u32(v)                       항상 도메인 바로 다음, seq보다 앞
 || u64(seq)
 || bytes(prev)                  32바이트 원본, hex가 아님
 || u64(ts)
 || bytes(session)               16바이트 원본
 || str(actor)
 || tag(enforcement)
 || enc(event)
 || tag(decision)
 || opt(str(rule))
)
```

`enforcement`는 `observe` = 1, `seatbelt` = 2, `landlock` = 3입니다.

`decision`은 `allow` = 1, `deny` = 2, `ask` = 3, `forbid` = 4입니다.

SHA-256을 택한 이유는 FIPS 180-4 승인 알고리즘이고 어떤 언어와 플랫폼에서도 독립 검증기를 만들 수 있기 때문입니다. 감사 증거의 가치는 Airlock 없이도 제3자가 검증할 수 있다는 데서 나오므로 속도보다 보편성을 우선합니다.

### 6.3 이벤트 인코딩

각 이벤트는 태그 1바이트로 시작하며, JSON 표현의 `type` 필드가 태그에 대응합니다.

```
0x01 session_start
     str(airlock_version) || list(str)(argv) || str(cwd)
  || bytes(policy_digest) || opt(str)(policy_source) || tag(fsync_per_entry)
  || tag(mediation) || u32(uid) || u32(euid)
  || opt(str)(operator) || opt(str)(policy_signer)
     mediation: 1 = off, 2 = exec-net, 3 = full

0x02 session_end
     tag(status_kind) || u32(status_value)
     status_kind: 1 = exited(값은 종료 코드), 2 = signaled(값은 시그널 번호), 3 = unknown(값은 0)

0x10 file_access
     str(path_requested) || str(path_resolved) || tag(mode)
     mode: 1 = read, 2 = write, 3 = create, 4 = delete, 5 = metadata, 6 = exec

0x11 exec
     str(program) || list(str)(argv) || str(cwd)

0x12 egress
     str(host) || u32(port) || tag(protocol)
     protocol: 1 = tcp, 2 = udp, 3 = tls, 4 = http

0x13 egress_summary
     str(host) || u32(port) || tag(protocol)
  || u64(bytes_out) || u64(bytes_in) || u64(duration_ms)

0x20 approval
     u64(for_seq) || tag(granted) || opt(str)(note)
  || opt(u64)(approver_uid) || opt(str)(approver_tty)
     granted: 1 = 승인, 2 = 거절, 3 = 응답 없음(타임아웃)

0x30 policy_reload
     bytes(policy_digest) || opt(str)(policy_source)
```

`policy_reload`은 실행 중 정책 교체 기능을 위해 태그를 **예약**해 둔 것이며 구현은 이 이벤트를 방출하지 않습니다. 세션 하나의 정책은 제네시스에 묶인 다이제스트로 고정됩니다. 인코딩과 검증 경로는 미리 정의해 두어, 기능이 들어올 때 태그 번호가 흔들리며 과거 체인이 깨지는 일이 없게 합니다.

`egress`의 프로토콜 태그는 관측한 층이 정합니다. seccomp 중계 층은 `connect(2)`의 소켓 타입까지만 보므로 항상 `tcp`입니다. egress 프록시 층은 요청 형태를 보고 CONNECT를 `tls`로, absolute-form 평문 요청을 `http`로 남깁니다([`egress-proxy.md`](./egress-proxy.md) 3절). `udp`는 방출되지 않습니다.

`egress_summary`는 **결정이 아니라 결과**를 담는 첫 이벤트입니다. `egress`가 "어디로 나가려 했고 무엇으로 판정했는가"를 남긴다면 `egress_summary`는 "그래서 실제로 얼마나 나갔는가"를 남깁니다. 연결이 끝난 뒤 프록시 층이 방출하며, 같은 연결의 `egress` 엔트리와는 `host`·`port`로 상관합니다. 바이트 수는 프록시가 실제로 중계한 페이로드 바이트이며 TLS 레코드 오버헤드를 뺀 값이 아닙니다. 상관 id가 없으므로 같은 목적지로의 동시 연결이 여럿이면 개별 연결을 되짚을 수 없고, 이는 알려진 한계입니다.

`egress_summary`는 판정이 아니므로 `decision`이 언제나 `allow`이고 `rule`은 예약 id `airlock:egress-summary`입니다. 규칙 없는 `allow`로 남기면 `[defaults]`가 열어 준 것처럼 보이므로, 판정이 아니라는 사실 자체를 규칙 자리에 적습니다. 이 이벤트를 방출하는 시점에 정책은 다시 평가하지 않습니다.

**이 이벤트는 프록시 층 전용입니다.** seccomp 중계 층은 `connect(2)`만 보고 그 뒤로 오가는 바이트를 보지 못하므로 결과를 만들 수 없습니다. 곧 `--egress-proxy` 없이 도는 세션에는 `egress_summary`가 하나도 없으며, 그 세션의 반출량은 **전혀 알 수 없습니다**. 엔트리가 없는 것을 "아무것도 나가지 않았다"로 읽으면 안 됩니다.

같은 이유로 **방향별 바이트를 세지 못한 연결에는 이 이벤트를 만들지 않습니다.** 0은 "아무것도 나가지 않았다"는 사실 주장이므로, 모르는 것을 0으로 기록하면 로그가 거짓 보증을 합니다. 허용된 `egress` 엔트리 수보다 `egress_summary` 수가 적으면 그 차이가 곧 "결과를 모르는 연결"이며, `airlock audit report`가 그 수를 따로 보여 줍니다.

세션이 끝난 뒤에 도착한 결과도 기록하지 않습니다. `session_end` 뒤에 붙는 엔트리는 체인을 앵커보다 길게 만들어 세션 전체를 "종료 후 덧붙이기"로 보고하게 만들기 때문입니다(8.3절). 브로커는 세션을 닫기 전에 살아 있는 중계 연결이 끝나기를 짧게 기다리며, 그 상한을 넘겨 도착한 결과는 경고로만 나갑니다.

프록시 모드에서는 같은 연결에 엔트리가 둘 남습니다. 중계 층이 `127.0.0.1:<프록시포트>`를, 프록시 층이 실제 목적지를 남깁니다. 중복이 아니라 서로 다른 사실이며, 둘을 합쳐야 "자식이 프록시로 갔고 프록시가 어디로 나갔다"가 복원됩니다. 중계 층 엔트리를 생략하면 프록시를 거치지 않은 연결 시도와 구분되지 않습니다.

`approval`의 `approver_uid`와 `approver_tty`는 **승인한 주체가 누구였는지**를 남깁니다. 둘 다 없으면 "사람이 승인했다"는 사실만 남고 "누가 승인했다"는 남지 않아, 승인이 사후에 책임 근거가 되지 못합니다. `approver_tty`는 승인 프롬프트가 실제로 나간 터미널 장치 경로이며, 관측할 수 없으면 `null`입니다. 관측할 수 없는데도 값을 지어내지 않습니다.

`file_access`가 요청 경로와 해석된 경로를 둘 다 담는 이유는 심볼릭 링크 우회 시도 자체가 증거이기 때문입니다. `~/link` 요청이 `~/.ssh/id_ed25519`로 해석되었다면 그 사실이 로그에 남아야 합니다. 둘 중 하나만 남기면 공격 시도가 정상 접근처럼 보입니다.

## 7. 검증 절차

`airlock audit verify`는 아래를 순서대로 확인하고, 실패 시 실패한 `seq`와 이유를 보고합니다.

1. 각 줄이 유효한 JSON이며 스키마에 맞는가
2. **`v`가 `2`인가.** 아니면 그 줄에서 즉시 멈추고 포맷 불일치로 보고합니다 (7.1)
3. `seq`가 0부터 빈틈 없이 1씩 증가하는가
4. `seq = 0`의 `prev`가 0 64자이고 이벤트가 `session_start`인가
5. 모든 `n > 0`에 대해 `entry[n].prev == entry[n-1].hash`인가
6. 각 엔트리의 `hash`를 6.2로 재계산한 값과 일치하는가
7. `ts`가 단조 비감소인가. 감소하면 경고로 보고하며, 벽시계 조정으로 정상 발생할 수 있으므로 실패로 처리하지 않습니다
8. 모든 `approval` 엔트리의 `for_seq`가 존재하고, 그 엔트리의 `decision`이 `ask`인가
9. `head.json`의 `seq`와 `hash`가 마지막 엔트리와 일치하는가

검증기는 체인을 스트리밍으로 처리합니다. 전체를 메모리에 올리면 큰 로그에서 검증 자체가 불가능해집니다.

### 7.1 포맷 버전 검사가 해시 검사보다 먼저다

2단계가 6단계보다 앞에 있는 것은 규범입니다. 순서를 바꾸면 v1 체인이 `HashMismatch`, 곧 **내용 변조 의심**으로 보고됩니다. 옛 포맷과 위조가 같은 실패로 보고되는 상태가 v1의 결함이었고 v2가 닫는 것이 정확히 그것입니다.

v1 체인은 변환하지 않고 거부합니다. 검증자는 "이 체인은 포맷 v1이며 이 검증자는 v2만 안다. 변조가 아니라 옛 포맷일 수 있으니 그 버전의 airlock으로 검증하라"는 취지로 보고합니다.

자동 변환을 넣지 않는 이유는 다음과 같습니다.

- 변환은 감사 로그를 **다시 쓰는** 일입니다. 원본 바이트가 사라지면 그 로그는 더 이상 관측 기록이 아니라 파생물이며, 파생물의 해시는 원본에 대해 아무것도 증명하지 못합니다.
- 변환기가 있으면 "변환된 것"과 "변환기를 흉내 낸 위조"가 다시 같은 모습이 됩니다. v1에서 닫으려던 구멍이 한 층 위에서 그대로 열립니다.
- 옛 체인을 읽는 올바른 방법은 그 포맷을 아는 검증자를 그대로 보존하는 것입니다. 포맷 버전이 in-band에 있으므로 어떤 검증자를 써야 하는지 로그 자체가 말해 줍니다.

`head.json`의 `version` 필드는 체인 포맷 버전이 아니라 그 파일 자신의 스키마 버전이며 `1`을 유지합니다. 둘을 같은 수로 묶으면 한쪽 변경이 다른 쪽을 강제로 끌고 갑니다.

### 7.2 head.json

```json
{
  "version": 1, 
  "seq": 42, 
  "hash": "...64자 hex...", 
  "session": "...32자 hex..."
}
```

`head.json`은 잘라내기 탐지 전용입니다. 4절 순서상 엔트리 append와 `head.json` 갱신 사이에 크래시가 나면 `head.json`이 한 칸 뒤처질 수 있으므로, 검증기는 `head.seq`가 마지막 엔트리보다 정확히 1 작고 체인 자체가 온전한 경우를 크래시 잔여로 보고 경고로 처리합니다. 그 외의 불일치는 실패입니다.

## 8. 세션 상위 앵커 체인

세션은 서로 독립된 체인이고 제네시스의 `prev`는 항상 0입니다. 그래서 세션 디렉토리를 통째로 지우면 남은 파일 어디에도 흔적이 없습니다. 앵커 체인은 세션 바깥에 세션마다 한 줄을 남겨 그 구멍을 좁힙니다.

### 8.1 파일과 스키마

파일은 `<audit-root>/anchors.jsonl` 하나이며 append-only JSONL입니다. 각 줄은 아래 필드를 갖습니다.

| 필드           | 타입     | 설명                                     |
|--------------|--------|----------------------------------------|
| `v`          | u32    | 앵커 포맷 버전. 지금은 항상 `1`                   |
| `seq`        | u64    | 앵커 체인 안의 번호. 0부터 1씩 증가                 |
| `ts`         | u64    | 앵커를 쓴 UTC 유닉스 시각, 나노초                  |
| `ts_rfc3339` | string | 사람이 읽는 표현. 해시 대상이 아님                   |
| `session`    | string | 앵커가 가리키는 세션 식별자, 16바이트 hex             |
| `head_seq`   | u64    | 그 세션 체인의 마지막 `seq`                     |
| `head_hash`  | string | 그 세션 체인의 마지막 `hash`, 32바이트 hex         |
| `prev`       | string | 이전 앵커 줄의 해시. 첫 줄은 0 64자                |
| `hash`       | string | 이 앵커 줄의 해시                             |

`v`에는 기본값이 없습니다. `v`가 없는 앵커 줄은 옛 포맷이 아니라 **손상**입니다. v1 이전의 앵커 포맷은 존재한 적이 없으므로, 그런 줄을 관대하게 받아들이면 없는 과거를 있는 것처럼 만들어 줄 뿐입니다.

### 8.2 정규 인코딩

```
ANCHOR_DOMAIN = "airlock.anchor.v1\x00"

hash = SHA-256(
    ANCHOR_DOMAIN
 || u32(v)
 || u64(seq)
 || bytes(prev)
 || u64(ts)
 || bytes(session)
 || u64(head_seq)
 || bytes(head_hash)
)
```

도메인이 감사 체인과 **반드시 달라야** 합니다. 같은 도메인을 쓰면 한쪽에서 만든 바이트열을 다른 쪽 검증자에게 먹이는 교차 프로토콜 공격이 열립니다. 앵커 줄의 `head_hash` 자리에 조작된 값을 넣어 엔트리 해시처럼 보이게 만드는 시도가 그것입니다.

### 8.3 검증

앵커 체인 자체의 검증은 감사 체인과 같은 순서를 따릅니다. 파싱 -> 버전 -> `seq` 무결번 -> 첫 줄 `prev == 0` -> `prev` 연결 -> 해시 재계산. 여기에 앵커 고유 검사 둘을 더합니다.

- **같은 세션이 같은 `head_seq`로 두 번 나타나면 실패입니다.** 앵커 줄의 재기록이나 복제를 뜻합니다.
- **같은 세션이 다시 나타났는데 `head_seq`가 이전보다 크지 않으면 실패입니다.** 세션 체인은 자라기만 하므로, 더 짧은 상태로 다시 앵커되는 것은 되감기입니다.

같은 세션의 `head_seq`가 이전보다 크면 통과이며 경고로 보고합니다. 세션 중간 체크포인트 앵커를 허용하기 위한 것입니다.

세션 체인과 앵커의 대조는 별도 단계입니다. 세션의 실제 `(head_seq, head_hash)`를 앵커 기록과 비교해 다르면 실패로 보고합니다. 이때 **체인이 앵커보다 길어도 실패**입니다. 앵커는 세션 종료 시점에 쓰므로, 앵커 이후에 자란 체인은 종료 뒤에 덧붙인 엔트리를 뜻합니다.

앵커 파일이 아예 없으면 "탐지 불가"로 보고합니다. 통과가 아닙니다. 없는 앵커를 조용히 넘기면 앵커를 지우는 것이 가장 값싼 공격이 됩니다.

`AnchorLog`는 이미 깨진 앵커 체인 위에 이어 붙이기를 거부합니다. 깨진 체인 뒤에 정상 줄을 쌓으면 그 뒤쪽이 정당해 보이고, 어디까지가 신뢰 가능한지가 사라집니다.

### 8.4 이 앵커가 막는 것과 막지 못하는 것

막는 것.

- 세션 디렉토리 통째 삭제. 앵커 줄이 남아 있으므로 "이 세션이 있었고 head가 무엇이었다"가 남습니다.
- 세션 체인 전체 재계산. `head.json`까지 다시 써도 앵커의 `head_hash`와 어긋납니다.
- 세션 종료 뒤 엔트리 덧붙이기. `head_seq`가 앵커보다 앞서 나갑니다.
- 앵커 줄 자체의 수정·삭제·재배치.

**막지 못하는 것.**

- **앵커 파일이 같은 디렉토리 트리에 있고 대상이 거기에 쓸 수 있으면 아무것도 막지 못합니다.** 세션 체인을 다시 계산할 수 있는 주체는 앵커 체인도 같은 비용으로 다시 계산합니다. 키도 서명도 없으므로 재계산에 필요한 비밀이 없습니다.
- 앵커 파일 자체의 삭제. 검증자는 "탐지 불가"라고 말할 수 있을 뿐 원래 무엇이 있었는지 복원하지 못합니다.
- 애초에 앵커되지 않은 세션. SIGKILL로 죽은 세션은 앵커 줄이 없고, 그 사실만으로는 크래시와 삭제를 구분하지 못합니다.
- 시각. `ts`는 벽시계이며 앵커도 같은 시계를 씁니다.

곧 앵커의 실질 탐지력은 **저장 위치의 분리**에서만 나옵니다. 다른 볼륨, 다른 계정 소유, 원격 append-only 마운트 중 하나가 아니면 이 파일은 크래시 탐지기이지 변조 탐지기가 아닙니다. 문서가 이 구분을 흐리면 사용자는 있지도 않은 보장을 믿게 됩니다.

## 9. 매일 이상여부 점검과 책임자 확인

로그를 남기는 것과 사람이 그 로그를 본 것은 다른 사실입니다. 8절까지가 전자를 다루고 이 절이 후자를 다룹니다. 대한민국 전자금융감독규정 시행세칙 별표 7 의 16번이 "원격으로 접속하여 수행한 모든 작업 내역을 기록하고 **매일 이상여부 점검** 실시 및 **책임자가 확인**" 을 요구하는 그 자리입니다.

### 9.1 `airlock audit report`

범위 안의 모든 세션을 검증하고 집계해 한 번에 보고합니다. cron 이나 launchd 에 그대로 걸 수 있도록 **판정이 종료 코드에 담깁니다.**

```
airlock audit report [--since YYYY-MM-DD] [--until YYYY-MM-DD] [--json]
                     [--anchor-dir DIR] [--strict-approval]
```

`--since` 는 그 날 00:00:00 UTC 부터, `--until` 은 그 날 23:59:59.999999999 UTC 까지를 포함합니다. 하루를 통째로 덮지 않으면 자정 근처 세션이 어느 날의 점검에도 들어가지 않습니다. 세션이 범위에 드는지는 제네시스의 `ts` 로 판정하며, 체인을 읽지 못한 세션은 디렉토리 이름의 나노초로 대신합니다.

세션마다 무결성, 앵커 대조, 결정 집계(`allow`/`deny`/`ask`/`forbid`), 승인 집계, 거부된 `exec` 목록, 목적지별 아웃바운드 시도와 반출·수신 바이트를 보고합니다. 승인 집계는 **사람 신원이 관측된 응답과 그렇지 않은 응답을 반드시 나눕니다.** `--yes` 자동 승인과 신원을 관측하지 못한 채널은 `approver_uid` 와 `approver_tty` 가 둘 다 없으므로 여기서 갈립니다.

### 9.2 종료 코드

| 코드   | 뜻                                                                 |
|------|-------------------------------------------------------------------|
| `0`  | 이상 없음                                                             |
| `2`  | **증거 이상.** 로그 자체를 믿을 수 없음                                          |
| `3`  | **운영 이상.** 로그는 믿을 수 있으나 그 안에 이상이 있음                                |
| `64` | 인자 오류. 날짜 형식이 잘못되었거나 `--since` 가 `--until` 보다 뒤임                    |
| `70` | 내부 오류. 보고 자체를 만들지 못함                                              |

둘이 함께 있으면 `2` 가 이깁니다. 증거를 믿을 수 없는 상태가 그 안의 내용보다 먼저 다루어져야 하기 때문입니다.

증거 이상(`2`)으로 세는 것.

- 세션 체인의 무결성 실패 (해시·`seq`·`prev`·`head` 불일치)
- `FormatVersionUnsupported`. 옛 포맷은 변조가 아니지만 이 검증자가 판정할 수 없으므로 통과로 보고하지 않습니다
- 앵커 대조 실패
- **앵커 없음.** 앵커 파일이 아예 없는 경우와 그 세션의 앵커 줄이 없는 경우를 모두 포함합니다
- **앵커에는 있는데 디렉토리가 없는 세션.** 남은 세션만 훑으면 세션 통째 삭제가 "이상 없음" 으로 보고됩니다
- 어떤 이유로든 세션을 읽지 못함
- 확인 체인(`reviews.jsonl`) 손상

운영 이상(`3`)으로 세는 것.

- 답을 받지 못한 `ask`
- `--strict-approval` 을 준 경우, 사람 신원 없이 **허용된** 승인. 신원 없는 거부는 아무것도 통과시키지 않았으므로 세지 않습니다

**판단 불가는 통과가 아닙니다.** 앵커 없음을 이상으로 세는 이유가 그것입니다. 매일 점검의 목적이 탐지인데 탐지 불가를 통과로 보고하면 점검이 거짓 보증을 합니다. 같은 이유로 읽지 못한 세션을 조용히 건너뛰지 않습니다.

확인 기록이 아예 없는 것(`reviews.jsonl` 부재)은 이상이 아니라 **표시 대상**입니다. 아직 아무도 점검하지 않았다는 사실을 그대로 보고하되 종료 코드는 올리지 않습니다. 마지막 확인 이후 새 세션이 있는 것도 표시 대상입니다. 그것을 이상으로 세면 세션이 하나 돌 때마다 종료 코드가 비영이 되어 이상 신호가 소음에 묻힙니다.

사람용 출력은 세션마다 목록에 상한을 두지만 **상한이 걸린 사실 자체를 반드시 함께 찍습니다.** 조용한 절단은 "전부 점검했다" 로 읽힙니다. `--json` 출력은 절단하지 않으며 색상 코드도 섞지 않습니다. JSON 스키마 이름은 `airlock.audit-report.v1` 입니다.

### 9.3 `airlock audit ack`

책임자가 점검했다는 사실을 append-only 체인에 남깁니다.

```
airlock audit ack [--since YYYY-MM-DD] [--until YYYY-MM-DD]
                  [--anchor-dir DIR] [--note TEXT] [--strict-approval]
```

파일은 `<audit-root>/reviews.jsonl` 이며 앵커와 같은 디렉토리에 둡니다. 각 줄은 아래 필드를 갖습니다.

| 필드              | 타입             | 설명                                        |
|-----------------|----------------|-------------------------------------------|
| `v`             | u32            | 확인 포맷 버전. 지금은 항상 `1`. 기본값 없음              |
| `seq`           | u64            | 확인 체인 안의 번호. 0부터 1씩 증가                    |
| `ts`            | u64            | 확인한 UTC 유닉스 시각, 나노초                       |
| `ts_rfc3339`    | string         | 사람이 읽는 표현. 해시 대상이 아님                      |
| `reviewer_uid`  | u32            | 감사 층이 `getuid(2)`로 직접 읽은 값                |
| `reviewer_euid` | u32            | 감사 층이 `geteuid(2)`로 직접 읽은 값               |
| `reviewer_tty`  | string \| null | 확인 명령이 붙어 있던 터미널 장치 경로. 관측하지 못하면 `null`   |
| `since`         | string \| null | 점검 범위 시작 날짜                               |
| `until`         | string \| null | 점검 범위 끝 날짜                                |
| `sessions`      | list           | 실제로 읽은 세션 식별자 목록                          |
| `report_digest` | string         | 점검한 리포트의 다이제스트, 32바이트 hex                 |
| `verdict`       | string         | `clean` \| `anomalous`                     |
| `note`          | string \| null | 확인자가 남긴 메모                                |
| `prev`          | string         | 이전 확인 줄의 해시. 첫 줄은 0 64자                   |
| `hash`          | string         | 이 확인 줄의 해시                                |

```
REVIEW_DOMAIN = "airlock.review.v1\x00"

hash = SHA-256(
    REVIEW_DOMAIN
 || u32(v)
 || u64(seq)
 || bytes(prev)
 || u64(ts)
 || u32(reviewer_uid) || u32(reviewer_euid) || opt(str)(reviewer_tty)
 || opt(str)(since) || opt(str)(until) || list(bytes)(sessions)
 || bytes(report_digest)
 || tag(verdict)                 clean = 1, anomalous = 2
 || opt(str)(note)
)
```

도메인이 감사 체인·앵커 체인과 **반드시 달라야** 합니다. 같은 도메인을 쓰면 한쪽에서 만든 바이트열을 다른 쪽 검증자에게 먹이는 교차 프로토콜 공격이 열립니다.

`reviewer_uid` 와 `reviewer_euid` 는 **감사 층이 직접 읽습니다.** 호출자가 넘길 수 있으면 남의 계정으로 확인한 것처럼 기록할 수 있습니다. 5.1절의 제네시스 `uid`·`euid` 와 같은 규율입니다. `reviewer_tty` 는 브로커가 직접 관측한 값만 담으며, 관측하지 못하면 `null` 이고 검증자가 경고로 보고합니다. **`null` 을 사람이 확인한 것으로 읽으면 안 됩니다.** 무인 스크립트가 찍은 도장과 구분되지 않기 때문입니다.

### 9.4 범위와 다이제스트의 결합

기록되는 다이제스트는 리포트 본문만의 것이 아니라 **범위와 함께 묶인 값**입니다.

```
REPORT_DOMAIN = "airlock.report.v1\x00"

report_digest = SHA-256(
    REPORT_DOMAIN
 || opt(str)(since) || opt(str)(until) || list(bytes)(sessions)
 || bytes(body)
)
```

`body` 는 리포트가 담은 사실들의 다이제스트이며 생성 시각은 들어가지 않습니다. 시각이 들어가면 같은 사실을 두 번 계산할 때마다 값이 달라져 확인 도장이 어떤 리포트도 가리키지 못합니다.

범위를 다이제스트 안에 묶는 이유는 하나입니다. **사람이 보지 않은 범위에 확인 도장을 옮겨 찍을 수 없어야 합니다.** `airlock audit ack` 는 리포트를 다시 계산해 그 범위와 다이제스트를 기록하며, 호출자가 다이제스트를 직접 넘기는 경로를 두지 않습니다. 어떤 확인 줄이 지금 계산한 리포트를 실제로 가리키는지는 범위와 다이제스트를 함께 대조해 판정합니다. 범위가 다르면 `ScopeMismatch`, 본문이 다르면 `DigestMismatch` 입니다.

### 9.5 이 체인이 막지 못하는 것

8.4절과 같습니다. 키도 서명도 없는 해시체인이므로 **이 파일에 쓸 수 있는 주체는 체인 전체를 같은 비용으로 다시 계산합니다.** 실질 탐지력은 저장 위치의 분리에서만 나옵니다.

그 밖에 이 체인이 주장하지 않는 것.

- `reviewer_uid` 는 확인 명령을 돌린 계정이지 그 계정 뒤에 앉은 사람이 아닙니다.
- `reviewer_tty` 가 `null` 인 것은 사람이 확인하지 않았다는 뜻이 아니라 터미널을 관측하지 못했다는 뜻입니다. 반대로 값이 있다고 해서 사람이 읽었다는 증거가 되지도 않습니다. 도장을 찍은 자리가 어디였는지만 남습니다.
- 마지막 확인 줄의 삭제는 체인 안에서 정합적입니다. 하루치 점검이 지워진 사실은 세션과 대조해야 드러나며, `airlock audit report` 가 마지막 확인 시각과 그 이후 세션 수를 함께 보여 주는 이유가 그것입니다.
- `ts` 는 감사 체인과 같은 벽시계입니다.

## 10. 저장 시 암호화를 위한 예약

향후 저장 시 암호화가 들어오더라도 **해시체인은 평문 정규 바이트 위에 유지하고 암호 봉투는 체인 밖에 둡니다.** 체인이 암호문 위에 서면 키를 가진 쪽만 검증할 수 있게 되어, 제3자 독립 검증이라는 이 포맷의 존재 이유가 사라집니다. v2 스키마는 이 경로를 배제하지 않습니다. 봉투는 파일 층에서 줄 단위 또는 파일 단위로 감싸며, 복호 결과 바이트가 6절의 정규 인코딩 입력과 정확히 같아야 합니다.

## 11. 테스트 의무

구현은 최소한 아래를 커버하는 테스트를 갖습니다. 각 항목은 실패해야 하는 상황을 실제로 만들어 검증기가 잡는지 확인합니다.

- 정상 체인 왕복. 쓰고 다시 읽어 검증 통과
- 엔트리 필드 하나 수정 -> 해당 seq에서 실패
- 중간 엔트리 삭제 -> seq 빈틈 탐지
- 엔트리 순서 뒤바꾸기 -> prev 불일치 탐지
- 유효한 형태의 엔트리를 중간에 삽입 -> prev 불일치 탐지
- 뒤쪽 잘라내기 -> `head.json` 불일치 탐지
- 정책 다이제스트만 다른 두 체인의 제네시스 해시가 다름
- 길이 접두 모호성. `actor`와 그다음 문자열의 경계를 옮긴 두 엔트리가 서로 다른 해시를 가짐
- `ask` 엔트리 없이 존재하는 `approval` -> 실패
- 빈 파일, 마지막 줄 개행 없음, 줄 중간에서 잘린 JSON 같은 부분 쓰기 상황
- 마지막 줄이 공백만 있고 개행이 없는 경우 -> 부분 쓰기로 실패. 눈에 보이지 않는 바이트를 조용히 넘기면 잘라내기 탐지에 구멍이 생김
- 중계 수준이 다른 두 세션의 제네시스 해시가 다름
- `v`를 1로 낮춘 줄 -> 포맷 불일치로 실패하며 해시 불일치로는 보고되지 않음
- `v` 필드가 아예 없는 v1 형태 줄 -> 같은 사유로 실패. 변환 흉내가 아니라 거부
- `v`를 바꾸고 해시를 다시 계산해도 v1 도메인으로 계산한 바이트와 일치하지 않음
- `uid`, `euid`, `operator`, `policy_signer`, `approver_uid`, `approver_tty`, `egress_summary`의 각 필드가 해시를 바꿈
- 앵커 줄 하나 삭제 -> 탐지
- 앵커 줄 하나 수정 -> 탐지
- 세션 체인을 통째로 재계산해 `head.json`까지 맞춰도 앵커와 대조하면 탐지
- 앵커 파일 없음 -> "탐지 불가"로 명확히 보고
- 같은 세션의 중복 앵커와 `head_seq` 되감기 -> 탐지
- 깨진 앵커 체인에 이어 붙이기 거부
- 확인 줄 하나 삭제·수정·재배치·복제 -> 탐지
- 확인 줄의 `reviewer_uid`나 `reviewer_tty`를 고치면 -> 탐지
- 확인 줄의 범위(`since`·`until`·`sessions`)를 고치면 -> 탐지
- 다른 범위에서 계산한 다이제스트로 찍은 도장 -> 범위 대조에서 거부
- 깨진 확인 체인에 이어 붙이기 거부
- `reviews.jsonl` 부재 -> "확인 기록 없음"으로 보고하되 이상으로 세지 않음
- 변조된 세션 체인이 있는 범위에서 `airlock audit report`가 비영으로 끝남
- 앵커가 없는 세션이 있는 범위에서 `airlock audit report`가 비영으로 끝남
- 앵커에는 있는데 디렉토리가 없는 세션 -> 비영으로 끝남
- 자동 승인만 있는 세션이 "사람이 확인함"으로 집계되지 않음
- `--json` 출력이 안정된 스키마로 파싱되고 색상 코드를 담지 않음
