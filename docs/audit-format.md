# 감사 로그 포맷 규격 (airlock.audit.v1)

`airlock-audit`이 구현하는 append-only 해시체인 로그의 규격입니다. 구현과 이 문서가 어긋나면 이 문서가 정본입니다.

## 1. 목표와 비목표

### 목표

- 브로커가 관측한 모든 중재 지점을 순서와 함께 기록합니다.
- 엔트리 하나를 고치거나 지우거나 끼워 넣으면 그 지점부터 체인이 깨집니다.
- 어떤 정책이 적용된 상태였는지 로그 자체로 증명합니다.
- 사람과 도구가 같이 읽을 수 있습니다.

### 비목표 (v1)

- 파일시스템 전체에 쓰기 권한을 가진 공격자로부터의 보호. 해시체인은 체인 전체를 다시 계산할 수 있는 공격자를 막지 못하므로 2절을 참고합니다.
- 실시간 원격 전송, 로그 회전, 압축

## 2. 이 포맷이 실제로 보장하는 것

해시체인만으로 "위조 불가능"이라고 말하면 거짓입니다. 정확한 경계는 다음과 같습니다.

| 공격자 능력                         | v1 결과                           |
|--------------------------------|---------------------------------|
| 로그 디렉토리에 쓰기 권한 없음 (샌드박스된 에이전트) | 변조 불가, 강제 층이 실제 보장을 제공          |
| 엔트리 일부만 수정/삭제/삽입               | 검증에서 반드시 탐지                     |
| 로그 파일 뒤쪽을 잘라냄 (truncation)     | 앵커 파일과 대조해 탐지                   |
| 체인 전체를 처음부터 재계산해 교체            | v1에서 탐지 불가, 하드웨어 서명이 로드맵에 있는 이유 |

곧 실제 강제력은 두 가지 조합에서 나옵니다. 첫째로 감사 디렉토리를 강제 층이 에이전트에게 쓰기 금지하고, 둘째로 해시체인이 그 방어가 뚫렸을 때 흔적을 남깁니다. 전자 없이 후자만으로는 부족하다는 사실을 제품이 숨기지 않습니다.

## 3. 저장 레이아웃

감사(audit) 세션 하나는 디렉토리 하나입니다.

```
<audit-dir>/
  chain.jsonl     엔트리 로그, 한 줄에 JSON 오브젝트 하나
  head.json       앵커. 마지막 seq와 해시
```

- `chain.jsonl`은 `O_APPEND`로만 엽니다. 기존 바이트를 덮어쓰는 경로는 구현에 존재하지 않습니다.
- 디렉토리 권한은 `0700`, 파일 권한은 `0600`으로 생성합니다.
- 강제 층은 이 디렉토리를 피보호 프로세스에 대해 쓰기 금지로 설정해야 합니다.

## 4. 쓰기 순서 (write-ahead)

결정을 기록한 다음에 행위를 허용합니다. 순서를 뒤집으면 허용된 행위가 로그에 없는 창이 생깁니다.

1. 정책을 평가해 결정을 얻습니다.
2. 엔트리를 `chain.jsonl`에 append하고 `fsync`합니다.
3. `head.json`을 갱신하고 `fsync`합니다.
4. 그다음에 비로소 행위를 허용하거나 거부합니다.

`ask` 결정은 사람이 답하기 전에 기록합니다. 승인 결과는 원래 엔트리를 고치는 것이 아니라 그 seq를 참조하는 별도 `approval` 엔트리로 append하며, 엔트리는 한번 쓰이면 불변(immutable)입니다. 이 규칙 덕분에 사용자가 답하지 않고 세션이 죽어도 시도 자체는 남습니다.

`fsync`는 엔트리마다 수행합니다. 감사 로그에서 배치 플러시는 크래시 시 구간 손실을 뜻하므로 기본값이 될 수 없습니다. 성능이 필요하면 명시적 옵션으로 열되, 그 사실을 세션 시작 엔트리에 기록합니다.

## 5. 엔트리 스키마

`chain.jsonl`의 각 줄은 아래 필드를 갖는 JSON 오브젝트입니다. 필드 순서는 가독성을 위한 관례이며 해시에는 영향이 없습니다(6절의 정규 인코딩이 순서를 고정합니다).

| 필드            | 타입             | 설명                                           |
|---------------|----------------|----------------------------------------------|
| `seq`         | u64            | 0부터 1씩 증가. 빈틈이 있으면 검증 실패                     |
| `ts`          | u64            | UTC 유닉스 시각, 나노초                              |
| `ts_rfc3339`  | string         | 사람이 읽는 표현. 해시 대상이 아니며 검증하지 않음                |
| `session`     | string         | 세션 식별자, 16바이트 랜덤의 소문자 hex                    |
| `actor`       | string         | 관측된 주체. 예 `pid:41233 claude`                 |
| `enforcement` | string         | `observe` \| `seatbelt` \| `landlock`        |
| `event`       | object         | 6.3의 태그된 유니온                                 |
| `decision`    | string         | `allow` \| `deny` \| `ask` \| `forbid`       |
| `rule`        | string \| null | 결정을 낸 규칙 id. 기본값 적용 시 null                   |
| `prev`        | string         | 이전 엔트리 해시의 소문자 hex 64자. 제네시스(genesis)는 0 64자 |
| `hash`        | string         | 이 엔트리 해시의 소문자 hex 64자                        |

`ts_rfc3339`이 해시 대상이 아닌 이유는 시각 렌더링 규칙이 바뀌어도 과거 체인이 깨지지 않게 하기 위함입니다. 권위 있는 값은 언제나 `ts`입니다.

### 5.1 제네시스 엔트리

`seq = 0`은 반드시 `session_start` 이벤트이고 `prev`는 0 64자입니다. 이 엔트리가 정책 다이제스트를 담으므로 체인 전체가 특정 정책 내용에 묶이며, 곧 "그 시점에 어떤 정책이 걸려 있었는가"를 로그만으로 증명할 수 있습니다.

제네시스는 관측 범위를 결정하는 두 값을 함께 담습니다.

- `argv`는 브로커를 띄운 실제 호출을 재구성할 수 있어야 합니다. 승인 통제를 포기하는 `--yes`처럼 결정의 의미를 바꾸는 플래그가 빠지면, 로그만 보고 그 세션의 승인이 사람 판단이었는지 자동이었는지 알 수 없습니다.
- `mediation`은 자식 프로세스의 syscall을 어디까지 브로커로 중계했는지입니다. **요청값이 아니라 그 플랫폼에서 실제로 적용된 값**을 기록합니다. 이 값이 없으면 `exec` 엔트리가 없는 체인이 "아무 일도 없었음"인지 "중계가 꺼져 있어 보이지 않았음"인지 구분되지 않습니다.

`enforcement`가 강제 층의 등급을 엔트리마다 밝히는 것과 같은 이유로 중계 수준도 로그에 남습니다. 강제되지 않은 기록이 강제된 기록처럼 보이지 않아야 한다는 원칙([`docs/design.md` 9.3](./design.md#93-강제-층-enforcer-트레이트-추상화-백엔드는-점진-도입))은 관측 층에도 그대로 적용됩니다.

## 6. 정규 인코딩

해시 입력은 JSON 텍스트가 아닙니다. JSON은 공백, 키 순서, 유니코드 이스케이프, 수 표기가 모두 비유일하므로 해시 입력으로 부적합하며, 대신 아래 길이 접두 이진 인코딩을 씁니다.

모든 가변 길이 필드에 길이 접두를 붙이는 이유는 연결 모호성을 없애기 위함입니다. 접두가 없으면 `("ab", "c")`와 `("a", "bc")`가 같은 바이트열이 되어 서로 다른 엔트리가 같은 해시를 갖습니다.

### 6.1 기본 요소

```
DOMAIN   = "airlock.audit.v1\x00"        도메인 분리 접두사
u64(n)   = n을 리틀엔디안 8바이트로
u32(n)   = n을 리틀엔디안 4바이트로
tag(n)   = n을 1바이트로
bytes(b) = u64(len(b)) || b
str(s)   = bytes(utf8(s))                정규화하지 않고 저장된 바이트 그대로
opt(x)   = tag(0)                        x가 없을 때
         = tag(1) || enc(x)              x가 있을 때
list(xs) = u64(len(xs)) || enc(xs[0]) || enc(xs[1]) || ...
```

문자열을 유니코드 정규화하지 않는 것은 의도된 것입니다. 경로 정규화는 정책 층의 책임이고([`docs/policy-dsl.md` 4절](./policy-dsl.md#4-경로-정규화)), 감사 로그는 관측된 바이트를 그대로 보존해야 합니다. 감사 층이 문자열을 손보면 원본 증거가 사라집니다.

### 6.2 엔트리 해시

```
hash = SHA-256(
    DOMAIN
 || u64(seq)
 || bytes(prev)                  32바이트 원본, hex가 아님
 || u64(ts)
 || bytes(session)               16바이트 원본
 || str(actor)
 || tag(enforcement)
 || enc(event)
 || tag(decision)
 || opt(str(rule))
)
```

`enforcement`는 `observe` = 1, `seatbelt` = 2, `landlock` = 3입니다.

`decision`은 `allow` = 1, `deny` = 2, `ask` = 3, `forbid` = 4입니다.

SHA-256을 택한 이유는 FIPS 180-4 승인 알고리즘이고 어떤 언어와 플랫폼에서도 독립 검증기를 만들 수 있기 때문입니다. 감사 증거의 가치는 Airlock 없이도 제3자가 검증할 수 있다는 데서 나오므로 속도보다 보편성을 우선합니다.

### 6.3 이벤트 인코딩

각 이벤트는 태그 1바이트로 시작하며, JSON 표현의 `type` 필드가 태그에 대응합니다.

```
0x01 session_start
     str(airlock_version) || list(str)(argv) || str(cwd)
  || bytes(policy_digest) || opt(str)(policy_source) || tag(fsync_per_entry)
  || tag(mediation)
     mediation: 1 = off, 2 = exec-net, 3 = full

0x02 session_end
     tag(status_kind) || u32(status_value)
     status_kind: 1 = exited(값은 종료 코드), 2 = signaled(값은 시그널 번호), 3 = unknown(값은 0)

0x10 file_access
     str(path_requested) || str(path_resolved) || tag(mode)
     mode: 1 = read, 2 = write, 3 = create, 4 = delete, 5 = metadata, 6 = exec

0x11 exec
     str(program) || list(str)(argv) || str(cwd)

0x12 egress
     str(host) || u32(port) || tag(protocol)
     protocol: 1 = tcp, 2 = udp, 3 = tls, 4 = http

0x20 approval
     u64(for_seq) || tag(granted) || opt(str)(note)
     granted: 1 = 승인, 2 = 거절, 3 = 응답 없음(타임아웃)

0x30 policy_reload
     bytes(policy_digest) || opt(str)(policy_source)
```

`policy_reload`은 실행 중 정책 교체 기능을 위해 태그를 **예약**해 둔 것이며 v1 구현은 이 이벤트를 방출하지 않습니다. 세션 하나의 정책은 제네시스에 묶인 다이제스트로 고정됩니다. 인코딩과 검증 경로는 미리 정의해 두어, 기능이 들어올 때 태그 번호가 흔들리며 과거 체인이 깨지는 일이 없게 합니다.

`file_access`가 요청 경로와 해석된 경로를 둘 다 담는 이유는 심볼릭 링크 우회 시도 자체가 증거이기 때문입니다. `~/link` 요청이 `~/.ssh/id_ed25519`로 해석되었다면 그 사실이 로그에 남아야 합니다. 둘 중 하나만 남기면 공격 시도가 정상 접근처럼 보입니다.

## 7. 검증 절차

`airlock audit verify`는 아래를 순서대로 확인하고, 실패 시 실패한 `seq`와 이유를 보고합니다.

1. 각 줄이 유효한 JSON이며 스키마에 맞는가
2. `seq`가 0부터 빈틈 없이 1씩 증가하는가
3. `seq = 0`의 `prev`가 0 64자이고 이벤트가 `session_start`인가
4. 모든 `n > 0`에 대해 `entry[n].prev == entry[n-1].hash`인가
5. 각 엔트리의 `hash`를 6.2로 재계산한 값과 일치하는가
6. `ts`가 단조 비감소인가. 감소하면 경고로 보고하며, 벽시계 조정으로 정상 발생할 수 있으므로 실패로 처리하지 않습니다
7. 모든 `approval` 엔트리의 `for_seq`가 존재하고, 그 엔트리의 `decision`이 `ask`인가
8. `head.json`의 `seq`와 `hash`가 마지막 엔트리와 일치하는가

검증기는 체인을 스트리밍으로 처리합니다. 전체를 메모리에 올리면 큰 로그에서 검증 자체가 불가능해집니다.

### 7.1 head.json

```json
{
  "version": 1, 
  "seq": 42, 
  "hash": "...64자 hex...", 
  "session": "...32자 hex..."
}
```

앵커 파일은 잘라내기 탐지 전용입니다. 4절 순서상 엔트리 append와 앵커 갱신 사이에 크래시가 나면 `head.json`이 한 칸 뒤처질 수 있으므로, 검증기는 `head.seq`가 마지막 엔트리보다 정확히 1 작고 체인 자체가 온전한 경우를 크래시 잔여로 보고 경고로 처리합니다. 그 외의 불일치는 실패입니다.

## 8. 테스트 의무

구현은 최소한 아래를 커버하는 테스트를 갖습니다. 각 항목은 실패해야 하는 상황을 실제로 만들어 검증기가 잡는지 확인합니다.

- 정상 체인 왕복. 쓰고 다시 읽어 검증 통과
- 엔트리 필드 하나 수정 -> 해당 seq에서 실패
- 중간 엔트리 삭제 -> seq 빈틈 탐지
- 엔트리 순서 뒤바꾸기 -> prev 불일치 탐지
- 유효한 형태의 엔트리를 중간에 삽입 -> prev 불일치 탐지
- 뒤쪽 잘라내기 -> 앵커 불일치 탐지
- 정책 다이제스트만 다른 두 체인의 제네시스 해시가 다름
- 길이 접두 모호성. `actor`와 그다음 문자열의 경계를 옮긴 두 엔트리가 서로 다른 해시를 가짐
- `ask` 엔트리 없이 존재하는 `approval` -> 실패
- 빈 파일, 마지막 줄 개행 없음, 줄 중간에서 잘린 JSON 같은 부분 쓰기 상황
- 마지막 줄이 공백만 있고 개행이 없는 경우 -> 부분 쓰기로 실패. 눈에 보이지 않는 바이트를 조용히 넘기면 잘라내기 탐지에 구멍이 생김
- 중계 수준이 다른 두 세션의 제네시스 해시가 다름
