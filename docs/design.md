# Airlock 설계 문서

## 1. 개요

Airlock은 AI 코딩 에이전트를 위한 로컬 제로 트러스트 게이트웨이입니다. 에이전트가 개발자 머신에서 수행하는 파일 접근, 프로세스 실행, 네트워크 연결을 경계에서 중재하고, 위험한 행위만 차단하거나 사람 승인을 받게 하며, 모든 행위를 변조 탐지 가능한 감사 로그(audit log)로 남깁니다.

핵심 전제는 하나입니다. 에이전트는 신뢰할 수 없는 코드 실행자입니다. LLM은 확률적이고 프롬프트 인젝션에 취약하므로, 에이전트가 무엇을 하려는지가 아니라 실제로 무엇을 하는지를 경계에서 강제합니다.

한 줄로 정의하면, 개발 편의는 유지하되 위험 행위만 세밀하게 잡고 증명 가능하게 기록하는 로컬 브로커(broker)입니다.

## 2. 왜 지금인가

Claude Code, Cursor, 자율 에이전트가 개발자 머신에서 파일을 읽고 코드를 실행하고 아웃바운드 연결을 만듭니다. 그러나 이 행위를 통제하는 보안 계층은 사실상 없습니다. 공격 표면 자체가 2024년 이후에 새로 생겼고, 아직 표준 방어책이 없습니다.

기존 도구로는 다음과 같은 이유로 해결되지 않습니다.

- 컨테이너나 VM 샌드박스는 무겁고, 로컬 파일 접근(에이전트의 존재 이유)을 막으면 쓸모가 없어집니다.
- 정적 seccomp 프로파일은 에이전트의 문맥을 모릅니다.
- Airlock은 세밀한 정책(위험 행위만 차단)과 증명 가능한 감사(무슨 일이 있었는지 증명)를 결합합니다.

## 3. 위협 모델

### 3.1 보호 대상

- 시크릿 (SSH 키, `.env`, 클라우드 자격증명, 브라우저 쿠키와 세션)
- 소스코드와 사용자 데이터
- 시스템 무결성

### 3.2 공격자와 위협

1. 간접 프롬프트 인젝션 (웹페이지, 이슈, 코드 코멘트, 의존성 README에 심긴 지시를 에이전트가 읽고 탈취 행위 수행)
2. 오염된 서드파티 MCP 서버 또는 툴
3. 오염된 의존성 (공급망 공격)
4. 정상 에이전트의 사고 (`rm -rf`, 잘못된 force push, 시크릿을 로그로 유출)
5. 데이터 반출 (시크릿을 읽어 아웃바운드 요청으로 유출)

### 3.3 신뢰 경계

Airlock 브로커만 신뢰 가능한 컴퓨팅 기반(Trusted Computing Base, TCB)입니다. 에이전트, 툴, MCP 서버, LLM은 전부 경계 밖에 둡니다. 정책과 감사 로그는 에이전트가 접근할 수 없는 별도 권한과 프로세스에 둡니다.

## 4. 아키텍처

### 4.1 3층 인터셉션

이식성 순에서 강제력 순으로 쌓습니다.

1. MCP 프록시 층
   에이전트와 MCP 서버 사이에 프록시를 끼워 JSON-RPC 레벨에서 모든 tool call을 관찰하고 정책을 적용하고 로깅합니다. 이식성이 높지만 에이전트가 직접 실행하는 bash는 MCP 밖이라 잡지 못합니다.

2. OS 강제 층 (강제력의 핵심)
   에이전트 프로세스를 격리 아래에서 실행하고 파일과 네트워크 syscall을 브로커로 중재합니다. Linux는 Landlock과 seccomp-bpf, macOS는 sandbox 프로파일을 사용합니다. `ptrace`나 `LD_PRELOAD`보다 우회가 어려우며, 실제 강제력은 여기서 나옵니다.

3. 네트워크 층
   에이전트 아웃바운드를 로컬 egress 프록시로 강제합니다. 도메인 allowlist를 적용하고, 시크릿 패턴이 페이로드에 보이면 차단합니다(DLP).

이상적으로는 세 층을 조합합니다. MVP는 OS 강제 층부터 시작해 강제력을 먼저 확보합니다.

### 4.2 정책 엔진

- capability 기반이며, 파일 경로와 exec, egress 도메인 각각에 대해 규칙을 둡니다.
- 결정은 `allow`, `deny`, `ask`(사람 승인), `forbid`(명시적 `overrides`로만 완화 가능한 deny) 4단계입니다. 자세한 의미론은 [`docs/policy-dsl.md` 3절](./policy-dsl.md#3-평가-의미론)에 있습니다.
- 시크릿 경로(`~/.ssh`, `~/.aws`, `.env`, 브라우저 프로필)는 기본 deny입니다.
- 위험 exec(`curl | bash`, `rm -rf /`)은 기본 ask입니다.
- 정책은 선언적 DSL로 표현합니다.

### 4.3 감사 로그 (차별화 핵심)

- append-only이며 해시체인으로 변조를 탐지합니다(tamper-evident).
- 각 엔트리는 시각, 행위, 인자, 정책 결정, 에이전트 신원을 담습니다.
- 강제 층이 감사 디렉토리 쓰기를 막으므로, 에이전트는 로그를 지우거나 위조할 수 없습니다.
- 이후 TPM이나 Secure Enclave 키로 서명하면 포렌식과 컴플라이언스 증거가 됩니다.
- "무슨 일이 있었는지 증명 가능"이 곧 제품 가치입니다.

## 5. 워크스페이스 구성

- `crates/airlock` 플래그십 바이너리. CLI 진입점(`run`, `audit`, `policy` 서브커맨드)
- `crates/airlock-broker` OS 강제 층. `Enforcer` 트레이트와 플랫폼별 백엔드, 프로세스 감독
- `crates/airlock-policy` capability 정책 모델과 `allow`/`deny`/`ask` 평가 엔진
- `crates/airlock-audit` 해시체인 append-only 감사 로그와 검증
- `crates/airlock-canonical` 길이 접두 정규 인코딩과 hex. 의존성 없는 리프

의존 방향은 한 방향으로 고정합니다. `airlock` -> `airlock-broker` -> {`airlock-policy`, `airlock-audit`} -> `airlock-canonical`이며, `airlock-policy`와 `airlock-audit`은 서로를 의존하지 않습니다. 코어 두 크레이트를 플랫폼과 무관하게, 그리고 서로 무관하게 유지하는 것이 목적입니다.

`airlock-canonical`을 별도 크레이트로 분리한 이유는 감사 엔트리 해시와 정책 다이제스트가 **같은** 정규 인코딩을 써야 하기 때문입니다. 두 곳에 복제하면 언젠가 갈라지고, 갈라지면 해시가 증명하는 대상이 달라집니다. 정책이 감사를 의존하게 만드는 대안은 코어 분리 원칙을 깨므로, 둘 아래에 의존성 없는 리프를 둡니다.

## 6. MVP 범위 (v1)

Rust로, 데모 가능하고 가치가 증명되는 최소 슬라이스만 만듭니다.

구현 순서는 플랫폼 무관 코어부터입니다. 감사 로그와 정책 엔진은 어느 OS에서도 완전히 테스트할 수 있고, 동시에 제품 차별화의 핵심입니다. 강제 층은 트레이트 뒤에서 백엔드를 갈아 끼우는 구조이므로 나중에 붙여도 위층 설계가 흔들리지 않습니다. 반대 순서로 가면 검증 불가능한 플랫폼 코드 위에 정책 모델을 얹게 됩니다.

1. 해시체인 감사 로그 포맷과 검증 (`airlock-audit`). 규격은 `docs/audit-format.md`
2. capability 정책 모델과 TOML DSL, 평가 엔진 (`airlock-policy`). 규격은 `docs/policy-dsl.md`
3. `Enforcer` 트레이트와 `observe` 백엔드 (`airlock-broker`)
4. `airlock run -- <cmd>` 래퍼와 `airlock audit` 뷰어, `/dev/tty` 인라인 ask 승인
5. OS 강제 백엔드. macOS Seatbelt -> Linux Landlock + seccomp
6. egress 프록시와 도메인 allowlist

1번부터 4번까지가 "관찰과 증명"이고 5번부터가 "강제"입니다. 4번 시점에 이미 프롬프트 인젝션 사후 조사에 쓸 수 있는 도구가 되며, 5번에서 예방으로 넘어갑니다. 강제가 붙기 전까지는 그 한계를 제품이 스스로 명시합니다([9.3](#93-강제-층-enforcer-트레이트-추상화-백엔드는-점진-도입) 참고).

현재 1번부터 5번까지 구현되어 있고 6번이 남아 있습니다. 5번에는 Linux 런타임 중계 층이 함께 들어가 자식 프로세스의 exec와 아웃바운드 연결이 감사에 남습니다. 이것이 없으면 `airlock run`이 직접 띄운 프로세스 하나만 기록되고 그 아래 자식들은 보이지 않습니다. **중계 층은 Linux 전용이므로 macOS는 지금도 세션 단위 기록만 남습니다.** 6번 egress 프록시 층이 들어오면 호스트 단위 정책과 함께 macOS의 아웃바운드 관측도 채워집니다.

## 7. 로드맵

MCP 프록시 층 -> egress DLP(시크릿 패턴 차단) -> 하드웨어 서명 -> 정책 프리셋 커뮤니티 순으로 진행합니다.

## 8. 해자와 리스크

### 해자

- 위험 경로와 도메인 정책 프리셋의 큐레이션 품질
- 인터셉션의 우회 불가능성
- 낮은 false positive로 개발자 마찰 최소화
- 감사 로그의 신뢰성

### 리스크

- 우회 (에이전트가 서브프로세스 스폰, 새 네트워크 경로 사용). OS 강제 층이 반드시 필요한 이유입니다.
- False positive로 인한 개발자 불편. 학습 모드와 정책 튜닝으로 대응합니다.
- macOS 강제 방식의 제약 (sandbox-exec는 구식 취급, ESF는 서명과 공증 필요).
- 사람 승인 피싱 (LLM이 그럴듯한 이유로 승인을 유도). ask 프롬프트에 충분한 원본 문맥을 노출합니다.

## 9. 확정 결정

### 9.1 라이선스: AGPL-3.0-only

보안 도구는 소스 검증 가능성이 신뢰의 전제입니다. 사용자가 자기 머신의 TCB를 직접 읽고 빌드해 확인할 수 있어야 합니다. AGPL은 네트워크 서비스 형태의 재판매에도 소스 공개를 요구하므로, 관리형 SaaS로 포크되어 감사 불가능한 블랙박스가 되는 경로를 막습니다. 상용 듀얼 라이선스 여지는 남겨 둡니다.

정본은 저장소 루트 `LICENSE`에 두고, 크레이트 메타데이터에는 `license = "AGPL-3.0-only"`를 명시합니다.

### 9.2 정책 DSL: TOML 기반 자체 선언적 DSL

Rego/OPA 차용은 기각했습니다. 근거는 세 가지입니다.

- TCB 최소화. 정책 평가기는 브로커 안에서 돌고, 곧 신뢰 경계 안입니다. 범용 정책 언어의 인터프리터 전체를 TCB에 넣으면 감사 표면이 불필요하게 넓어집니다.
- air-gapped 이식성. 의존성이 적어야 vendoring과 재현 빌드가 쉽습니다.
- 결정 가능성. Airlock 정책은 튜링 완전할 필요가 없습니다. 유한한 매칭과 순서 규칙으로 충분하고, 그래야 "이 정책이 무엇을 허용하는가"를 정적으로 답할 수 있습니다.

문법과 평가 의미론은 [`docs/policy-dsl.md`](./policy-dsl.md)에 규격으로 분리했습니다.

### 9.3 강제 층: `Enforcer` 트레이트 추상화, 백엔드는 점진 도입

`airlock-broker`는 OS별 구현을 `Enforcer` 트레이트 뒤로 숨깁니다. 정책 모델과 감사 로그는 플랫폼에 의존하지 않습니다.

백엔드 도입 순서와 강제력 등급은 분리해 표기합니다.

| 백엔드                                       | 플랫폼   | 강제 범위                    | 강제력               | 상태  |
|-------------------------------------------|-------|--------------------------|-------------------|-----|
| `observe`                                 | 전 플랫폼 | 없음                       | 없음 (기록만)          | 구현됨 |
| Seatbelt (`sandbox_init_with_parameters`) | macOS | 파일 경로, exec 경로, 아웃바운드 전체 | 커널 강제, 우회 난이도 중   | 구현됨 |
| Landlock                                  | Linux | 파일 경로(inode), TCP 포트     | 커널 강제, 우회 난이도 높음  | 구현됨 |
| seccomp user notification                 | Linux | exec, connect, 선택적 open  | 관측과 승인 채널. 강제는 아님 | 구현됨 |
| Endpoint Security Framework               | macOS | -                        | 커널 강제, 시스템 전역     | 로드맵 |

**강제 범위가 플랫폼마다 다르다는 사실 자체를 제품이 노출합니다.** 같은 정책 파일이 두 OS 에서 같은 결론을 내지 않습니다. macOS는 exec경로를 커널에서 막을 수 있지만 argv 조건은 볼 수 없고 포트 단위 egress도 표현할 수 없습니다. Linux는 포트까지 강제하지만 exec는 커널이 아니라 중계 층에서 판정합니다. 옮기지 못한 규칙은 조용히 버리지 않고 enforcer의 gap 목록에 담아 배너로 출력합니다. 미강제를 침묵하면 감사 로그가 거짓 보증을 하게 됩니다.

`ask` 는 커널이 표현할 수 없어 백엔드마다 다르게 내려갑니다. 파일 규칙은 deny로 강하하고, macOS의 exec 규칙은 **프로파일에 넣지 않습니다.** macOS에서 답을 받을 수 있는 ask는 브로커가 spawn 전에 묻는 최상위 exec 하나뿐인데, 그것을 deny로 내리면 사람이 승인한 실행이 커널에서 막혀 어떤 방법으로도 진행할 수 없기 때문입니다. 이 비대칭은 gap으로 노출합니다.

**중계 수준도 강제력 등급과 같은 취급을 받습니다.** 요청한 `--mediate` 값이 그 플랫폼에서 적용되지 않으면(macOS 에는 중계 기구가 없습니다) 배너가 요청값과 적용값을 함께 보여 주고, 감사 로그 제네시스에는 **실제로 적용된 값**을 기록합니다. 이 값이 없으면 `exec` 엔트리가 없는 체인이 "아무 일도 없었음"인지 "보이지 않았음"인지 구분되지 않습니다.

Landlock은 **allow만 표현할 수 있고 규칙이 inode에 걸립니다.** deny 규칙을 그대로 옮길 수 없고 허용한 하위 트리 안에서 일부만 빼는 것도 불가능하므로, 백엔드는 규칙을 번역하는 대신 허용할 트리를 실제로 순회하며 거부 결정이 나는 항목을 빼는 방식으로 계획을 세웁니다. 하위에 거부 대상이 없는 디렉토리는 통째로 한 규칙이 되어 규칙 수가 시크릿 경로의 깊이에 비례합니다. 순회 비용이 시작 시간을 지배하지 않도록, 어떤 규칙에도 닿을 수 없는 항목은 값싼 사전 필터로 걸러 냅니다.

seccomp user notification 층은 강제 층이 아니라 **관측과 승인 채널**입니다. 자식 프로세스가 부르는 `execve`/`connect`와, 선택적으로 `openat`을 브로커로 중계해 감사 엔트리를 남기고 `ask` 승인을 받습니다. 이 층이 없으면 에이전트가 스폰한 자식 프로세스의 행위가 감사 로그에 전혀 남지 않습니다. 다만 인자를 읽은 시점과 커널이 실제로 여는 시점 사이에 링크가 바뀔 수 있어 구조적으로 TOCTOU를 부담하므로([10.1절](#101-landlock은-호스트-단위-네트워크-정책을-표현할-수-없다)), 파일 접근의 실제 경계는 Landlock이고 이 층은 그 위의 기록 층입니다.

`observe` 백엔드를 1순위로 둔 것은 철학적 개발 타협이 아니라 설계 요구사항입니다. 강제 없이 기록만 하는 모드는 학습 모드(false positive 튜닝)와 정책 드라이런의 기반이고, 8장에서 식별한 "false positive로 인한 개발자 불편" 리스크의 직접적 대응책입니다.

강제력이 없는 모드는 반드시 그 사실을 노출합니다. `observe` 아래에서 기록된 감사 엔트리는 `enforcement: "observe"` 필드를 갖고, `airlock audit`은 이를 명시적으로 표시합니다. 강제된 로그와 관찰된 로그를 구분 없이 보여 주면 감사 로그가 거짓 보증을 하게 됩니다.

### 9.4 ask 승인 UX: `/dev/tty` 직결 인라인 프롬프트

브로커가 제어 터미널을 직접 열어 승인을 묻습니다. 에이전트의 stdin/stdout/stderr와 물리적으로 분리된 채널이므로, 에이전트가 승인 프롬프트를 위조하거나 자기 출력으로 사용자 입력을 가로챌 수 없습니다. 이는 8장의 "사람 승인 피싱" 리스크 대응의 핵심입니다. TUI는 이 채널 위에 얹는 표현 계층이며 별도 결정 사항이 아닙니다.

승인 프롬프트는 에이전트가 제공한 설명이 아니라 브로커가 관측한 원본 사실(정규화된 절대 경로, argv 배열 원본, 매칭된 규칙과 그 근거)만 표시합니다. 에이전트가 만든 문자열은 승인 화면에 넣지 않습니다.

## 10. 기술 제약 (2026-07 조사 기준)

개발 전 조사 작업에서 확인된 제약이며, 설계를 바꾸는 사실만 남깁니다.

> [!IMPORTANT]
> 장 타이틀의 조사 기준일을 잘 확인해주세요. 이 문서는 지속적으로 변하기 떄문에 당장은 불필요하더라도 필요합니다.
> 

### 10.1 Landlock은 호스트 단위 네트워크 정책을 표현할 수 없다

`landlock` crate 0.4.6은 ABI v1~v8을 지원합니다. TCP 제어는 ABI v4(Linux 6.7)부터 가능하지만, `landlock_net_port_attr`가 받는 것은 **포트뿐입니다**. IP도 호스트명도 규칙에 넣을 수 없습니다. UDP 제어는 ABI v10에서야 들어왔고 crate에 아직 없습니다.

따라서 "`api.qu4nt.space`만 허용" 같은 [4.2절](#42-정책-엔진) egress 정책은 Landlock으로 구현할 수 없으며, 두 경로 중 하나를 택해야 합니다.

- network namespace와 로컬 egress 프록시로 아웃바운드를 강제 경유시킵니다. 호스트명과 TLS SNI를 볼 수 있고 DLP까지 확장되지만 netns 설정이 필요합니다.
- seccomp user notification으로 `connect`를 가로채 `sockaddr`을 검사합니다. netns가 불필요하지만 IP만 보이므로 호스트명 정책은 DNS 관측과 묶어야 하고, 구조적으로 TOCTOU를 부담합니다.

MVP는 전자를 택합니다. 후자는 IP 기반 정책까지만 표현할 수 있어 [4.2절](#42-정책-엔진) 요구사항을 만족하지 못합니다.

현재 Linux 백엔드는 Landlock ABI v4 이상에서 **포트 단위까지** 강제합니다. 정책에 호스트 패턴이나 IP 리터럴이 있으면 그 사실을 경고와 gap 으로 노출합니다. 그와 별개로 seccomp 중계 층이 `connect`의 `sockaddr`을 읽어 IP 와 포트를 감사에 남기므로, 호스트 단위 강제는 아직 없어도 무엇으로 나갔는지는 사후에 증명할 수 있습니다.

### 10.2 seccomp user notification은 순수 Rust로 완결되지 않는다

`seccompiler` 0.5.0은 `SECCOMP_RET_USER_NOTIF` 액션을 제공하지 않습니다(Allow/Errno/Kill/Log/Trace/Trap만 제공). user notification이 있는 성숙한 crate는 `libseccomp` 0.4.0뿐이고, 이는 C `libseccomp >= 2.5.0` FFI를 끌어옵니다.

air-gapped 재현 빌드 원칙과 충돌하므로 방침을 미리 정합니다. user notification이 필요한 필터는 `libc`의 `seccomp_notif` 구조체로 직접 조립합니다. C 의존성은 TCB에 넣지 않습니다.

구현 결과 필요한 것은 user notification 하나뿐이라 `seccompiler`도 넣지 않았습니다. BPF 프로그램은 아키텍처 확인, syscall 번호 비교, `SECCOMP_RET_USER_NOTIF` 또는 `SECCOMP_RET_ALLOW` 반환으로 끝나며 `libc` 위에서 직접 만듭니다. 새로 추가된 런타임 의존성은 Landlock 백엔드의 `landlock` crate(순수 Rust)뿐입니다.

**`Command::spawn`과 execve 중계는 서로를 막습니다.** `spawn`은 자식이 exec을 마쳐야 돌아오는데, 그 exec 자체가 알림으로 멈춰 있으므로 같은 스레드에서 listener를 기다리면 교착합니다. 감독 스레드를 `spawn`보다 먼저 띄워 listener 수신을 그 스레드에서 대기시킵니다.

### 10.3 macOS는 deprecated public API 위에 짓는 것 외에 선택지가 없다

- `sandbox_init(3)`은 10.8부터 헤더가 deprecated지만 계속 동작합니다. 서명도 entitlement도 필요 없습니다. **Darwin 25.4 arm64(macOS 26.4)에서 동작 확인.** Chromium과 Apple 자체 앱이 여전히 사용합니다.
- Endpoint Security Framework는 AUTH 이벤트로 진짜 차단을 할 수 있는 유일한 공식 경로지만, `com.apple.developer.endpoint-security.client` entitlement에 Apple 개별 승인과 유료 개발자 프로그램, notarization이 필요합니다. 무서명 로컬 오픈소스 도구가 쓸 수 없으므로 기업 배포판 옵션으로만 남깁니다.
- Network Extension도 유료 개발자와 system extension 패키징이 필요하므로 MVP 밖입니다.

적용 패턴은 fork 후 `pre_exec`에서 `sandbox_init_with_parameters()`를 호출하고 exec하는 방식입니다. 프로필을 임시 파일로 떨어뜨리지 않고 문자열로 직접 넘깁니다.

브로커는 `/usr/bin/sandbox-exec`를 쓰는 두 번째 경로도 갖고 있으나 교차 검증 전용입니다. 생성한 SBPL을 Apple 자신의 도구로 걸어 보아 프로필이 실제로 의도한 것을 막는지 FFI 경로와 독립적으로 확인합니다. 이 방식은 프로필 전문이 argv에 실려 같은 머신의 다른 프로세스에게 `ps`로 보이므로 CLI는 선택하지 않으며, 선택되면 그 사실을 enforcer의 gap 목록에 노출합니다.

**프로필은 반드시 deny-default로 작성합니다.** allow-default 프로필에 예외를 쌓는 방식은 2026년에 공개된 실제 탈출 사례가 있습니다. 또한 OS 마이너 버전이 올라가면 이전에는 참조하지 않던 리소스를 셸이 읽어 거부가 발생하는 회귀가 관측되므로(Tahoe의 `hw.*` sysctl), OS 버전별 프로필 회귀를 테스트 매트릭스로 방어합니다. 현재 CI 는 GitHub Actions 의 macOS 러너 하나(`macos-15`)만 돌립니다. 여러 OS 버전 매트릭스는 러너 이미지가 제공되는 범위 안에서 늘려야 하며, 지금은 그 사실을 한계로 적어 둡니다.

SBPL 로 표현할 수 있는 범위와 표현할 수 없는 범위는 아래와 같습니다. 표현할 수 없는 것을 표현한 척하는 것이 가장 위험하므로 목록을 고정합니다.

| 정책                 | SBPL 표현 | 방식                                                          |
|--------------------|---------|-------------------------------------------------------------|
| 파일 경로 allow/deny   | 가능      | `literal`, `subpath`, `regex`. 제한 규칙은 NFC 및 NFD 두 형태를 함께 방출 |
| exec 경로/파일 이름 deny | 가능      | `(deny process-exec* ...)`. 파일 이름만 지정한 규칙은 `regex`          |
| exec argv 조건       | **불가능** | 커널이 argv 를 프로파일 판정에 넘기지 않음                                  |
| 아웃바운드 전체 차단        | 가능      | `network-outbound` 규칙을 방출하지 않음 (deny-default)               |
| 포트/호스트 단위 egress   | **불가능** | 프록시 층이 필요함                                                  |
| `ask`              | **불가능** | 사람 승인을 표현할 수 없음                                             |

### 10.4 선행 구현이 존재한다

`nono` 0.69.0(Landlock과 Seatbelt 기반 capability 샌드박스, 누적 13.9만 다운로드)과 `sandlock-core` 0.8.5는 Airlock의 강제 층과 아키텍처가 상당 부분 겹칩니다. 곧 **OS 샌드박싱 자체는 차별화 요소가 아닙니다.**

Airlock의 차별점은 4.3절 그대로 감사 로그입니다. 무슨 일이 있었는지 제3자가 검증 가능한 형태로 증명하는 것, 정책 결정과 그 근거를 체인에 묶는 것, ask 승인을 피싱 불가능한 채널로 받는 것입니다. 강제 층은 그 증명을 신뢰할 수 있게 만드는 토대이지 제품 그 자체가 아니며, 6장의 구현 순서가 이 판단과 일치합니다.

### 10.5 감사 로그 구현은 외부 crypto 라이브러리에 강하게 결합하지 않는다

systemd journald의 Forward Secure Sealing이 gcrypt deprecation과 함께 배포판에서 사실상 비활성화된 선례가 있습니다. 해시 함수는 교체 가능한 지점 뒤에 두고, v1은 순수 Rust SHA-256만 씁니다.

`ct-merkle` 0.3.0(RFC 6962 append-only 로그, 832 LOC, no_std)은 inclusion proof와 consistency proof를 제공합니다. v1의 prev-hash 체인보다 강한 성질이며, 제3자 witness와 앵커 공개가 필요해지는 시점의 업그레이드 경로로 둡니다. v1에 넣지 않는 이유는 단일 로컬 사용자에게 아직 필요 없는 복잡성이기 때문입니다.

## 11. 남은 미결 사항

- 감사 로그 하드웨어 서명 키 보관 (TPM 2.0 vs Secure Enclave vs 소프트웨어 키링)
- 정책 프리셋 배포와 갱신 채널 (서명된 번들 형태)
- egress 프록시의 TLS 처리 (SNI 관측만 vs MITM 종단). MITM은 DLP를 가능하게 하지만 로컬 CA 주입이 필요하고 그 자체가 공격 표면입니다.
