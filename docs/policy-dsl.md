# 정책 DSL 규격 (airlock.policy.v2)

`airlock-policy` 크레이트가 구현하는 capability 정책의 문법과 평가 의미론적 문서입니다. 구현과 이 문서가 어긋나는 경우엔 이 문서가 정본이므로 구현을 수정해야 합니다.

## 이 문서에 나오는 주체

무엇이 무엇을 하는지 헷갈리지 않도록, 등장하는 다섯 주체를 먼저 정리합니다. 아래 본문에서 "누가" 하는 일인지는 이 표를 기준으로 읽으면 됩니다.

| 주체          | 하는 일                                                             |
|-------------|------------------------------------------------------------------|
| **사용자**     | 정책 파일(TOML)을 작성합니다.                                              |
| **정책 엔진**   | 정책 파일을 읽어 검사하고, 요청 하나에 `allow`/`deny`/`ask`/`forbid` 중 하나로 답합니다. |
| **브로커**     | 정책 엔진의 답을 실행에 옮깁니다. 사람에게 승인을 묻고, 감사 로그를 쓰고, 커널 프로파일을 만듭니다.       |
| **커널 강제 층** | 실제로 접근을 차단합니다. macOS는 Seatbelt, Linux는 Landlock입니다.              |
| **에이전트**    | 정책의 적용을 받는 쪽입니다. AI 코딩 에이전트와 그 자식 프로세스 전부를 말하며, 신뢰 경계 밖입니다.      |

## 자주 나오는 용어

| 용어           | 의미                                                                                                       |
|--------------|----------------------------------------------------------------------------------------------------------|
| **규칙**       | 정책 파일의 `[[rules]]` 항목 하나                                                                                 |
| **요청**       | 에이전트가 하려는 행위 하나("이 파일을 읽겠다", "이 프로그램을 실행하겠다", "이 호스트로 연결하겠다")                                            |
| **결정**       | 요청 하나에 대해 정책 엔진이 낸 답                                                                                     |
| **티어**       | 규칙 묶음의 우선순위 등급. 번호가 작을수록 먼저 봅니다([3절](#3-평가-의미론)).                                                        |
| **예외 허용**    | 내장 `forbid` 규칙이 막는 범위 중 일부를 사용자 규칙으로 다시 여는 것. 다른 문서에서 "완화"라고 부르는 것과 같습니다([3.2절](#32-forbid와-overrides)). |
| **probe 경로** | `forbid` 규칙이 "최소한 이것만은 반드시 막는다"고 선언한 대표 경로([3.3절](#33-효력-없는-예외-규칙-찾아내기))                                 |

## 1. 설계 원칙

- **정책은 실행 없이 답할 수 있어야 합니다.**
  - 정책 언어는 튜링 완전(Turing complete)하지 않습니다. "이 정책은 이 경로에 어떤 결정을 내는가"를 에이전트를 실제로 돌려 보지 않고 알 수 있어야 하며, `airlock policy explain` 명령이 이 성질 위에 서 있습니다.
- **애매하면 좁은 쪽으로 답합니다.**
  - 판단이 갈리는 상황에서 정책 엔진은 항상 더 제한적인 결정을 냅니다. 정책 파일을 읽다 실패하면 "일단 열어 두고 넘어가기"가 아니라 로드 자체를 거부합니다.
- **시크릿 보호를 여는 데는 근거가 필요합니다.**
  - 사용자는 시크릿 보호에 예외를 둘 수 있지만, 어떤 보호를 왜 여는지 적지 않으면 정책 엔진이 파일을 로드하지 않습니다.
- **적히지 않은 것은 허용이 아닙니다.**
  - 어떤 규칙에도 매칭되지 않은 요청은 `[defaults]`가 적용됩니다. 그리고 `[defaults]`조차 `allow`로 둘 수 없는 항목이 있습니다.

## 2. 파일 구조

```toml
version = 1
name = "claude-code-default"

[defaults]
file             = "ask"
exec             = "ask"
egress           = "deny"
egress_plaintext = "deny"

[[rules]]
id     = "workspace-rw"
kind   = "file"
path   = "~/work/airlock/**"
mode   = ["read", "write", "create", "delete"]
action = "allow"

[[rules]]
id     = "env-files"
kind   = "file"
path   = "**/.env*"
action = "deny"
reason = "환경 변수 시크릿"

[[rules]]
id     = "danger-rm"
kind   = "exec"
program = "rm"
argv_contains = ["-rf"]
action = "ask"

[[rules]]
id     = "llm-endpoint"
kind   = "egress"
host   = "api.anthropic.com"
port   = 443
action = "allow"

[[rules]]
id       = "legacy-plaintext-mirror"
kind     = "egress"
host     = "mirror.internal.example"
port     = 80
protocol = "http"
action   = "allow"
reason   = "TLS를 지원하지 않는 사내 미러. 평문을 여는 것을 알고 적음"
```

### 2.1 공통 필드

| 필드          | 필수  | 설명                                                                                                   |
|-------------|-----|------------------------------------------------------------------------------------------------------|
| `id`        | 예   | 영숫자와 `.` `_` `-` `:` 만 쓸 수 있음. 파일 내에서 유일하고 내장 규칙 id와 겹치지 않을 것. 감사 로그의 `rule` 필드에 기록되므로 안정적인 이름을 쓸 것  |
| `kind`      | 예   | `file` \| `exec` \| `egress`                                                                         |
| `action`    | 예   | `allow` \| `deny` \| `ask`. `forbid`는 내장 베이스라인 전용이며 사용자 규칙에 쓰면 로드 거부 ([3.2절](#32-forbid와-overrides)) |
| `reason`    | 조건부 | 사람이 읽는 근거. `overrides`를 쓸 때 필수                                                                       |
| `overrides` | 아니오 | 예외를 두려는 내장 `forbid` 규칙의 id                                                                           |

정책 엔진이 모르는 키가 하나라도 있으면 로드를 거부하며, 그 키를 무시하고 넘어가지 않습니다. 예를 들어 `mode`를 `modes`로 잘못 적은 경우, 그 키를 조용히 무시하면 `mode` 자체가 없는 규칙이 되고, `mode`가 없으면 **모든 모드에 적용**되므로([6절](#6-file-규칙)) 사용자가 의도한 것보다 훨씬 넓은 규칙이 아무 신호 없이 살아납니다.

### 2.2 `[defaults]`

어떤 규칙에도 매칭되지 않은 요청에 정책 엔진이 낼 답을 kind별로 하나씩 정합니다.

| 키                  | 기본값    | 쓸 수 있는 값                              | 비고                                                     |
|--------------------|--------|---------------------------------------|--------------------------------------------------------|
| `file`             | `ask`  | `allow` \| `deny` \| `ask`             |                                                        |
| `exec`             | `ask`  | `allow` \| `deny` \| `ask`             |                                                        |
| `egress`           | `deny` | `deny` \| `ask`                        | `allow`는 로드 거부                                         |
| `egress_plaintext` | `deny` | `allow` \| `deny` \| `ask`             | `allow`는 로드는 되지만 경고 ([8.2절](#82-평문-아웃바운드-바닥)) |

`egress`에는 `allow`를 쓸 수 없고, 쓰면 정책 엔진이 로드를 거부합니다. 아웃바운드를 기본 허용으로 두는 것은 데이터 반출([위협 모델 3.2](./design.md#32-공격자와-위협)의 5번)에 대한 방어를 통째로 포기하는 설정이라, 아예 문법 단계에서 쓸 수 없도록 구현되어 있습니다.

네 키 모두 `forbid`를 쓸 수 없습니다. `forbid`는 내장 베이스라인 전용입니다.

`egress_plaintext`는 다른 셋과 성격이 다릅니다. "매칭되는 규칙이 없을 때의 답"이 아니라 **평문 아웃바운드가 넘을 수 없는 상한**이며, 어떤 규칙이 매칭되었든 그 위에 한 번 더 적용됩니다. 의미론은 [8.2절](#82-평문-아웃바운드-바닥)에 있습니다.

## 3. 평가 의미론

요청 하나가 들어오면 정책 엔진은 규칙 묶음을 아래 순서대로 봅니다. 이 순서를 티어(tier)라고 하며, 첫 번째 매칭만이 적용됩니다.

```
0. 자기보호 규칙        브로커가 직접 넣습니다. 정책 파일로 쓸 수도, 예외를 둘 수도 없습니다.
1. 내장 forbid 규칙    이 규칙을 overrides 로 지목한 사용자 규칙만 앞설 수 있습니다.
2. 사용자 규칙          정책 파일에 적힌 순서대로 보고, 처음 매칭된 규칙이 답합니다.
3. 내장 ask/deny 규칙  정의된 순서대로 보고, 처음 매칭된 규칙이 답합니다.
4. [defaults]        여기까지 아무것도 매칭되지 않았을 때 kind별 기본값이 답합니다.
---
5. 평문 바닥          egress 질의가 평문일 때만 도는 후처리입니다. 티어가 아닙니다 (8.2절).
```

5번은 티어가 아니라 0번부터 4번까지가 낸 답 **위에** 한 번 더 씌우는 상한입니다. `egress` 질의에만 돌고 `file`과 `exec`에는 돌지 않습니다. 규격은 [8.2절](#82-평문-아웃바운드-바닥)에 있습니다.

**같은 티어 안에서는 처음 매칭된 규칙이 답합니다**(first-match-wins). "가장 구체적인 규칙이 답한다" 방식을 택하지 않은 이유는 '예측 가능성'입니다. 구체성을 비교하는 규칙 자체가 미묘한 버그의 온상이고, 무엇보다 사용자가 자기 정책 파일을 읽고 결과를 예측하기 어려워집니다. 선언 순서를 쓰면 위에서 아래로 읽어 내려가면 그만입니다.

### 3.0 왜 forbid가 사용자 규칙보다 위인가

티어 순서가 만약 자기보호 -> 사용자 -> 베이스라인이었다고 가정해 봅시다. 그러면 가장 흔하고 가장 정당해 보이는 규칙 하나가 시크릿 보호를 통째로 무너뜨립니다.

```toml
[[rules]]
id = "workspace"
kind = "file"
path = "~/work/**"
action = "allow"
```

사용자 규칙이 베이스라인보다 먼저 매칭되므로 `~/work/api/.env`를 읽는 요청도 이 규칙에 걸려 허용됩니다. 사용자는 "내 작업 공간을 열었다"고만 생각했는데, 실제로는 그 안에 있던 애플리케이션 시크릿의 보호까지 함께 없앤 셈입니다.

이것을 로드 시점 오류로 처리하면 더 나빠집니다. 작업 공간을 여는 모든 정책이 `overrides = "env-files"`를 함께 적어야 하고, 사용자는 의미를 따지지 않고 습관적으로 `overrides`를 붙이게 되며, 결국 방어가 형식적인 절차로 전락합니다.

그래서 `forbid`를 사용자 규칙보다 위에 두었습니다. 결과는 두 가지입니다.

- 넓은 `allow` 규칙이 시크릿을 열지 못합니다. 위 `workspace` 규칙은 그대로 써도 되고, `.env`와 `~/.ssh`는 계속 보호됩니다.
- 예외는 `overrides`로 대상을 콕 집었을 때만 생깁니다. 곧 "시크릿은 기본 차단, 열려면 명시적 근거"라는 원칙이 사후 검사가 아니라 평가 구조 자체로 보장됩니다.

### 3.1 자기보호 규칙 (티어 0)

브로커가 세션마다 직접 넣는 규칙입니다. 사용자는 이 규칙을 정책 파일로 표현할 수도, 없앨 수도, 예외를 둘 수도 없습니다. `overrides`로 지목해도 적용되지 않습니다.

| 대상                                            | 결정     |
|-----------------------------------------------|--------|
| 감사 디렉토리 (`chain.jsonl`, `head.json`) 쓰기/생성/삭제 | `deny` |
| 활성 정책 파일 쓰기/생성/삭제                             | `deny` |
| Airlock 바이너리 자신 쓰기/생성/삭제                      | `deny` |

감사 로그를 기록당하는 쪽이 고쳐 쓸 수 있으면 그 로그는 증거가 아닙니다. 정책 파일을 통제받는 쪽이 고쳐 쓸 수 있으면 그 정책은 강제가 아닙니다. 이 두 가지는 사용자와 협상할 대상이 아니므로 정책 언어 밖에 두었습니다.

감사 디렉토리를 **읽는** 것은 티어 0에서 다루지 않습니다. **사용자가 자기 감사 로그를 에이전트에게 보여 주고 싶은 정당한 경우**가 있어서 예외를 둘 수 있어야 하는데, 티어 0에 넣으면 예외 자체가 불가능해지기 때문입니다.

읽기는 베이스라인에도 넣지 않고 `[defaults].file`로 흘려보냅니다. 기본값이 `ask`라면 사람에게 물어보게 되므로 조용히 통과하지는 않습니다. 같은 대상을 베이스라인에 한 번 더 적지 않는 이유는 두 가지입니다.

- 같은 대상을 두 티어에서 규정하면 둘이 언젠가 어긋나고, 그때 어느 쪽이 진짜인지 알 수 없게 됩니다.
- 베이스라인 규칙은 [11절](#11-정책-다이제스트)의 다이제스트 계산에 포함됩니다. 그런데 감사 디렉토리 경로는 머신마다 다르므로, 이것을 베이스라인에 넣으면 같은 정책 파일이 머신마다 다른 다이제스트를 내게 되어 정책 비교가 불가능해집니다.

### 3.2 `forbid`와 `overrides`

`forbid`는 "열고 싶으면 이 규칙을 이름으로 지목하라"는 조건이 붙은 `deny`입니다. 내장 베이스라인에서만 쓰며, 사용자 규칙에 `action = "forbid"`를 적으면 정책 엔진이 로드를 거부합니다.

`forbid`가 매칭되어도 정책 엔진은 그 자리에서 바로 끝내지 않고 한 가지를 더 확인합니다. **같은 요청에 매칭되면서 그 `forbid` 규칙의 id를 `overrides`에 적은 사용자 규칙이 있는가**를 봅니다. 있으면 그 사용자 규칙이 답하고, 없으면 `forbid`가 답합니다.

이렇게 예외를 두는 규칙은 아래 두 조건을 모두 만족해야 하며, 하나라도 어기면 정책 엔진이 로드를 거부합니다.

- `overrides`가 실제로 존재하는 내장 `forbid` 규칙의 id를 가리킬 것
- `reason`이 비어 있지 않을 것

```toml
[[rules]]
id        = "read-ssh-config"
kind      = "file"
path      = "~/.ssh/config"
mode      = ["read"]
action    = "allow"
overrides = "ssh-private-keys"
reason    = "배포 대상 호스트 별칭을 읽어야 함. 개인키는 별도 forbid로 유지"
```

이 규칙은 `ssh-private-keys`라는 `forbid`가 막고 있는 `~/.ssh/**` 중에서 `~/.ssh/config` 읽기 하나만 다시 엽니다. 나머지는 그대로 막힌 채입니다.

두 조건을 만족하면 예외를 둔 사실이 감사 로그의 정책 다이제스트에 그대로 남습니다. 곧 "누가 언제 어떤 근거로 시크릿 보호를 열었는가"를 나중에 증명할 수 있습니다.

> [!IMPORTANT]
> **커널 프로파일 한계**
> 
> 현재 macOS Seatbelt 프로파일은 위 예외를 반영하지 않습니다. SBPL(Seatbelt Policy Language)로는 "이 forbid가 막는 것 중 이 부분만 빼기"라는 교집합을 표현할 수 없고, 예외 규칙의 패턴을 deny 뒤에 통째로 allow로 내보내면 같은 경로에 겹쳐 있던 다른 forbid까지 함께 열리기 때문입니다.
>
> 그래서 macOS에서는 정책 엔진이 허용한 경로를 커널이 여전히 차단합니다. 정책 계층보다 커널이 더 좁게 판정하는 fail-closed 방향이라 위험하지는 않지만, 두 계층의 결론이 다르다는 사실 자체를 숨기지는 않습니다. `airlock run`이 시작할 때 배너의 한계 목록에 이 사실을 출력합니다.

### 3.3 효력 없는 예외 규칙 찾아내기

[3.0절](#30-왜-forbid가-사용자-규칙보다-위인가)의 티어 순서 덕분에, `overrides` 없이 시크릿을 열려고 한 사용자 규칙은 **보안의 측면에서 구멍이 아니라 그냥 아무 일도 하지 않는 규칙**이 됩니다.

**문제는 사용자가 그 사실을 모른다는 점**입니다. 자기가 쓴 규칙이 동작한다고 믿고 있는데 실제로는 무시되고 있는 상태이며, 조용히 무효한 규칙은 조용히 뚫리는 규칙만큼이나 나쁩니다.

그래서 정책 엔진은 로드 시점에 이런 규칙을 찾아 경고합니다. 패턴끼리의 교집합을 일반적으로 계산하지는 않고, 대신 각 내장 `forbid` 규칙이 자신을 대표하는 **구체적인 경로 몇 개**를 함께 선언해 둡니다. 이것을 probe 경로라고 합니다.

```
ssh-private-keys  probes: ~/.ssh/id_rsa, ~/.ssh/id_ed25519, ~/.ssh/identity
aws-credentials   probes: ~/.aws/credentials, ~/.aws/config
env-files         probes: ~/proj/.env, ~/proj/api/.env.production
```

로드할 때 정책 엔진은 각 probe 경로를 모든 파일 모드에 대해 **사용자 규칙만으로** 평가해 봅니다. 결과가 `allow`나 `ask`인데 그 사용자 규칙에 해당 `forbid`를 지목한 `overrides`가 없다면, 그 규칙은 시크릿을 열려다 실패한 규칙이므로 경고를 냅니다. 로드는 성공하며, 실제 결정은 `forbid`가 내므로 안전한 상태 그대로입니다.

패턴 대수 대신 구체적인 probe 경로를 쓰는 이유는 판정이 실제로 실행 가능하고 테스트 가능하기 때문입니다. probe 목록은 곧 "우리가 반드시 막겠다고 약속한 것"의 명세가 됩니다. 구현은 모든 `forbid` 규칙이 probe를 하나 이상 갖는지, 그리고 각 probe가 자기 규칙에 실제로 매칭되는지를 테스트로 검사합니다.

### 3.4 결정 결과

정책 엔진이 낸 결정 네 가지에 대해 브로커가 하는 일입니다.

| 결정       | 브로커 동작                                                                                      |
|----------|---------------------------------------------------------------------------------------------|
| `allow`  | 요청을 통과시킵니다. 감사 엔트리를 남깁니다                                                                    |
| `deny`   | 요청을 거부합니다. 감사 엔트리를 남깁니다. 에이전트 쪽에는 권한 오류로 보입니다 (macOS Seatbelt는 `EPERM`)                     |
| `ask`    | 감사 엔트리(`ask`)를 남기고 -> `/dev/tty`로 사람에게 승인을 묻고 -> `approval` 엔트리를 남긴 뒤 -> 그 답대로 통과시키거나 거부합니다 |
| `forbid` | `deny`와 똑같이 동작합니다. 둘의 차이는 로드 시점 의미론에만 있습니다 ([3.2절](#32-forbid와-overrides))                  |

`ask`인데 사람이 답하지 않거나 제어 터미널이 없으면 브로커는 **거부**합니다. 물어볼 방법이 없다고 통과시키면 `ask`가 사실상 `allow`로 조용히 내려앉기 때문입니다.

예외는 `airlock run --yes` 하나뿐입니다. 이 플래그는 모든 `ask`를 사람 확인 없이 승인합니다. 승인 통제를 스스로 포기하는 설정이므로 브로커가 시작할 때 경고를 내고, 각 `approval` 엔트리에 자동 승인이었다는 note를 남깁니다. 앞 문단의 조용한 내려앉음과 다른 점은 사용자가 명시적으로 선택했고 그 사실이 감사 로그에 남는다는 것입니다.

승인 프롬프트에 값을 표시하기 전에 브로커는 제어 문자와 양방향 재정렬 문자를 눈에 보이는 형태로 바꿉니다. 경로와 argv는 에이전트가 만들어 낸 신뢰할 수 없는 입력이고, 이스케이프 시퀀스가 그대로 터미널에 나가면 에이전트가 승인 화면을 다시 그려 사용자를 속일 수 있기 때문입니다([`docs/design.md` 9.4](design.md#94-ask-승인-ux-devtty-직결-인라인-프롬프트)).

## 4. 경로 정규화

실제 우회가 일어나는 지점입니다. 정책 엔진은 규칙과 대조하기 전에 요청 경로에 아래를 순서대로 적용합니다.

1. 첫 NUL 바이트에서 경로를 자릅니다. 커널은 C 문자열을 받으므로 NUL 뒤는 존재하지 않는 것과 같습니다.
2. `~`를 홈 디렉토리로 펼칩니다. `~user` 형태는 v1에서 지원하지 않으며 로드를 거부합니다.
3. 상대 경로면 그 시점의 cwd를 기준으로 절대 경로로 만듭니다.
4. **요청 경로**를 만듭니다. `.`과 빈 세그먼트를 지우고 `..`를 문자열 수준에서 해소합니다. 루트보다 위로 올라가는 `..`는 루트에서 멈춥니다.
5. **해소 경로**를 만듭니다. 4번의 문자열 정리를 하기 **전**의 절대 경로에서 심볼릭 링크를 먼저 따라간 다음, 그 결과에 문자열 정리를 적용합니다. 커널이 링크를 먼저 따라가고 `..`를 나중에 적용하기 때문이며, 순서를 뒤집어 `..`를 먼저 지우면 `link/..` 같은 경로가 커널이 실제로 여는 곳과 다른 곳을 가리키게 됩니다.
   - 경로가 통째로 존재하면 커널의 `realpath`가 곧 답입니다.
   - 존재하지 않으면(대상이 아직 없는 링크, 아직 만들어지지 않은 꼬리) 루트부터 한 구성 요소씩 걷습니다. 링크를 만나면 그 대상을 남은 구성 요소 앞에 끼워 넣고, **상대 대상은 그 시점까지 해소된 부모에 붙입니다.** 어휘적 부모에 붙이면 `ws/dir -> /out/dir`, `/out/dir/x -> ../id_rsa`에서 커널은 `/out/id_rsa`를 여는데 엔진은 `ws/id_rsa`를 판정해 작업 공간 규칙으로 열어 버립니다. `..`는 그 시점까지 해소된 경로에서 한 단계 올라갑니다.
   - 없는 구성 요소를 만나면 거기서 멈추고, 존재하는 접두는 디스크에 적힌 대소문자로 맞춘 뒤 나머지를 문자열로 이어 붙입니다.
   - 링크는 40홉까지 따라갑니다. 넘으면 커널이 `ELOOP`를 내는 자리이며, 그 시점까지 해소된 경로에 나머지를 문자열로 붙여 판정합니다.
6. **firmlink 접기 (macOS).** `/Users/x/.ssh`와 `/System/Volumes/Data/Users/x/.ssh`는 firmlink로 같은 디렉토리인데 `realpath`는 firmlink를 넘지 않아 후자를 후자로 돌려줍니다. 그대로 두면 `~/.ssh/**` forbid를 포함한 전 티어가 후자를 놓칩니다. 그래서 요청 경로와 해소 경로 양쪽에서 `/System/Volumes/Data/<대상>/...`을 `/<루트>/...`로 접습니다. 대상은 `/usr/share/firmlinks`(한 줄에 `<루트 경로>\t<Data 상대 경로>`)에 있는 것으로 한정하며, 표는 root 소유이고 다른 사용자가 쓸 수 없을 때만 읽고 내용은 데이터로만 다룹니다(절대 경로가 아닌 루트, 상대 경로가 아닌 Data 열, `.`/`..`/NUL이 섞인 줄은 버림). 표를 읽지 못하면 macOS 10.15 이후의 내장 기본 목록으로 물러섭니다. APFS 시스템 볼륨은 대소문자를 구분하지 않으므로 접두와 대상은 ASCII 대소문자를 무시하고 맞춥니다. Linux에는 firmlink가 없으므로 이 단계는 아무것도 하지 않습니다.

같은 접기를 **규칙 경로**에도 적용합니다. `Pattern` 파싱, 자기보호 규칙의 리터럴 경로, 그리고 아래 5절의 해소 변형(`/etc` -> `/private/etc`) 전부에서 앞쪽 고정 구간을 접으므로, 정책이 어느 표기로 적혀 있든 요청이 어느 표기로 오든 하나로 수렴합니다. 다이제스트는 적힌 그대로의 패턴 문자열로 계산하므로 접기의 영향을 받지 않습니다.

곧 하나의 요청에서 경로가 두 개 나옵니다. 에이전트가 적어 낸 **요청 경로**와, 링크를 따라간 끝에 실제로 닿는 **해소 경로**입니다. `airlock policy explain`은 둘 다 접힌 뒤의 표기로 보여 줍니다.

### 4.1 요청 경로와 해소 경로 양쪽으로 평가한다

`ln -s ~/.ssh /tmp/x`를 만들어 두고 `/tmp/x/id_ed25519`를 읽는 것은 결국 `~/.ssh/id_ed25519`를 읽는 것입니다. 그런데 요청 경로만 문자열로 정리해서는 이것을 잡을 수 없습니다. `/tmp/x/id_ed25519`라는 문자열 어디에도 `.ssh`가 없기 때문입니다.

그래서 정책 엔진은 **요청 경로와 해소 경로 둘 다를 평가하고, 그중 더 제한적인 결정을 채택합니다.** 제한 강도는 `forbid` > `deny` > `ask` > `allow` 순입니다. 위 예에서 요청 경로는 아무 규칙에도 걸리지 않아 `[defaults]`로 가더라도, 해소 경로가 `forbid`에 걸리므로 최종 결정은 `forbid`입니다.

브로커는 두 경로를 모두 감사 엔트리에 남깁니다(`docs/audit-format.md` 6.3의 `file_access`). 둘이 다르다는 사실 자체가 우회 시도의 증거이기 때문입니다.

### 4.2 TOCTOU

정책 엔진이 경로를 파악한 시점과 커널이 실제로 파일을 여는 시점 사이에는 짧은 틈이 있습니다. 그 사이에 링크가 다른 곳을 가리키도록 바뀌면 검사한 대상과 열리는 대상이 달라집니다. 경로를 기준으로 중재하는 방식이 원리적으로 안고 가는 한계입니다.

- **Landlock**은 경로가 아니라 inode에 규칙을 걸기 때문에 이 문제를 겪지 않습니다. Linux에서 실제 강제력이 여기서 나오는 이유입니다.
- **seccomp user notification 기반 중재**는 `notify_id_valid()` liveness 확인과 dirfd 기준 경로 해석을 반드시 수행합니다.
- **`observe` 백엔드**는 애초에 차단을 하지 않으므로, 여기서 TOCTOU는 보안 문제가 아니라 기록 정확도 문제입니다. 그래도 [4.1절](#41-요청-경로와-해소-경로-양쪽으로-평가한다)의 양방향 평가는 그대로 수행합니다.

### 4.3 대소문자와 유니코드

macOS APFS는 기본적으로 대소문자를 구분하지 않습니다. 곧 `~/.SSH/id_rsa`와 `~/.ssh/id_rsa`는 같은 파일입니다. 정책 엔진이 대소문자를 구분해서 비교하면 에이전트가 `~/.SSH/`로 접근하는 것만으로 시크릿 `deny` 규칙을 통째로 빠져나갑니다.

그렇다고 항상 대소문자를 무시하면 이번에는 `allow` 규칙이 사용자가 의도한 것보다 넓어집니다.

그래서 규칙의 `action`에 따라 비교 방식을 다르게 정의합니다. 기준은 하나입니다. **어느 쪽으로 실수하든 거부 방향이어야 합니다.**

| 규칙의 action              | 매칭 방식                              | 근거                                     |
|-------------------------|------------------------------------|----------------------------------------|
| `forbid`, `deny`, `ask` | ASCII 대소문자 무시 + 유니코드 NFC 정규화 후 재비교 | 넓게 잡아야 안전. `.SSH`도, NFD 표기도 함께 걸림      |
| `allow`                 | 바이트 그대로 비교                         | 좁게 잡아야 안전. `.Ssh`도 NFD 변형도 실수로 열지 않음   |

차단 규칙은 넓게 잡아 놓치지 않고, 허용 규칙은 좁게 잡아 새지 않습니다. 이 비대칭의 근거는 이것뿐이며, 편의를 위한 예외는 두지 않습니다.

**유니코드 정규화.** APFS는 정규화 형태를 구분하지 않으므로 NFC로 쓴 이름과 NFD로 쓴 같은 이름이 같은 파일을 가리킵니다. 바이트만 비교하면 `~/작업/*.pem` 같은 비ASCII `deny` 규칙을 NFD 표기로 접근해 빠져나갈 수 있습니다. 그래서 차단 규칙은 바이트 비교가 빗나가면 양쪽을 NFC로 접어 한 번 더 비교합니다. ASCII로만 된 세그먼트는 정규화해도 그대로이므로 추가 비용 없이 건너뜁니다.

비대칭의 이유는 대소문자와 같습니다. `allow`는 정규화 형태를 넘나들며 넓어지지 않습니다. 정규화를 구분하는 볼륨(일부 네트워크 마운트)에서는 NFC와 NFD가 진짜로 다른 파일이고, 그런 곳에서 `allow`가 양쪽에 걸리면 사용자가 열려고 하지 않은 경로까지 열리기 때문입니다.

**커널 계층.** macOS Seatbelt는 정규식으로 비교하기 전에 경로를 자체적으로 정규화하므로, 커널 프로파일 쪽은 원래 이 우회에 안전합니다(NFC/NFD 각 표기로 만든 파일과 각 표기의 접근, 네 가지 조합을 실측으로 확인했습니다). 그럼에도 브로커는 차단 규칙을 프로파일에 두 형태로 모두 내보냅니다. 커널 동작에 대한 가정을 하나라도 줄이는 값이 규칙 몇 줄 늘어나는 비용보다 크기 때문입니다. `allow` 규칙은 위와 같은 이유로 한 형태만 내보냅니다.

## 5. glob 문법

정책 엔진은 패턴을 `/`로 나눈 세그먼트 열로 해석합니다.

| 토큰   | 의미                              |
|------|---------------------------------|
| `**` | 세그먼트 전체일 때만 유효. 0개 이상의 세그먼트에 매칭 |
| `*`  | 세그먼트 안의 0개 이상의 바이트. `/`를 넘지 않음  |
| `?`  | 세그먼트 안의 정확히 한 바이트. `/`를 넘지 않음   |

v1에는 문자 클래스(`[abc]`)와 중괄호 확장(`{a,b}`)이 없습니다. 매처는 보안 경계이므로 표현력보다 검증 가능성을 택했습니다.

매칭은 유니코드 문자가 아니라 **바이트** 단위로 합니다. 유닉스에서 경로는 임의의 바이트열이고 유효한 UTF-8이라는 보장이 없습니다. 문자열로 변환해 매칭하면 UTF-8이 아닌 경로가 변환 과정에서 손상되어 시크릿 규칙을 빗나갈 수 있습니다. 그래서 `?`는 한 문자가 아니라 한 바이트에 매칭하며, 비 ASCII 이름에 `?`를 쓰는 것은 권장하지 않습니다.

`**`는 패턴 하나에 최대 4개까지만 쓸 수 있습니다. `**`가 중첩되면 백트래킹 비용이 세그먼트 수에 대해 지수적으로 늘어날 수 있는데, 경로는 에이전트가 만드는 신뢰할 수 없는 입력이기 때문입니다.

나머지 규칙은 다음과 같습니다.

- `a/**`는 `a` 자신과 그 아래 전부에 매칭합니다. 넓게 해석하는 쪽이 deny 규칙에 안전합니다.
- `**`가 세그먼트의 일부로 나타나면(`a**b`) 로드를 거부합니다. `*`로 오해할 소지를 없애기 위해서입니다.
- 패턴은 `~` 확장 후 절대 경로여야 합니다. `/`나 `~/`로 시작하지 않으면 로드를 거부합니다. 다만 `**/`로 시작하는 패턴과 `**` 단독은 "위치를 가리지 않음"을 뜻하는 관용 표현이므로 허용합니다(`**/.env*`).
- 매칭은 정규화된 경로에 대해 수행하며, 패턴 자체에는 `.`이나 `..`를 쓸 수 없습니다.

## 6. `file` 규칙

```toml
[[rules]]
kind = "file"
path = "~/.aws/**"
mode = ["read", "write", "create", "delete", "metadata", "exec"]
action = "deny"
```

`mode`를 생략하면 모든 모드에 적용됩니다. 생략했을 때 넓어지는 쪽이므로 deny 규칙에 안전한 기본값입니다.

`path`에는 패턴 하나를 문자열로 쓰거나, 여러 패턴을 배열로 쓸 수 있습니다. 배열은 같은 `id`와 같은 `mode`를 공유하는 패턴 묶음이며, 각 패턴을 [5절](#5-glob-문법) 문법으로 따로 검증합니다.

```toml
path = ["~/.netrc", "~/_netrc"]
```

`read`와 `write`를 구분하는 것은 위협 모델에서 의미가 있습니다. 시크릿을 `read`하는 것은 반출이고 `write`하는 것은 지속성 확보입니다. 다만 시크릿 경로에 대해서는 둘 다 막는 것이 기본입니다.

`metadata`는 `stat` 계열입니다. 파일의 존재 여부만으로도 정보가 새는 경우가 있지만, 개발 도구가 워낙 광범위하게 쓰기 때문에 기본 정책에서 `metadata`만 따로 막지는 않습니다.

## 7. `exec` 규칙

```toml
[[rules]]
kind = "exec"
program = "rm"
argv_contains = ["-rf"]
argv_pattern = "*/dev/*"
action = "ask"
```

| 필드              | 의미                                                                                                            |
|-----------------|---------------------------------------------------------------------------------------------------------------|
| `program`       | basename 또는 절대 경로. basename이면 어느 위치에 있든 같은 이름의 프로그램에 매칭. `/`를 포함하면 5절 glob으로 해석하므로 `/usr/bin/*` 같은 패턴도 쓸 수 있음 |
| `argv_contains` | 나열한 문자열이 argv에 **모두** 있어야 매칭. argv 원소 하나와 통째로 같아야 하며 부분 문자열 일치가 아님                                            |
| `argv_pattern`  | argv를 `\x00`으로 이어 붙인 문자열에 대한 glob                                                                             |

`program`과 `argv_contains`의 비교는 [4.3절](#43-대소문자와-유니코드)의 비대칭을 그대로 따릅니다. 곧 `forbid`/`deny`/`ask` 규칙은 ASCII 대소문자를 무시하고, `allow` 규칙은 바이트 그대로 비교합니다. `rm -RF`와 `SUDO`가 베이스라인 ask에 걸리는 이유이며, 양쪽 모두 거부 방향으로 실수합니다.

### 7.1 exec 규칙의 한계를 분명히 한다

**프로그램 경로는 커널 경계입니다.** `[defaults].exec`이 `allow`가 아닌 정책에서는 두 강제 백엔드 모두 exec을 화이트리스트로 겁니다. `program`으로 허용한 경로와 최상위 명령만 실행되고, 목록에 없는 프로그램은 커널이 `execve` 자체를 거부합니다. `[defaults].exec = "allow"`인 정책은 이 뒤집기를 하지 않습니다. 그 설정이 이미 "실행은 기본 허용"이라고 말하고 있기 때문입니다.

**`argv` 조건은 여전히 보안 경계가 아니라 tripwire이자 UX 계층입니다.** 아래 이야기는 `argv_contains`와 `argv_pattern`에만 해당합니다.

argv를 보고 판정하는 방식은 원리적으로 우회 가능합니다. `sh -c 'r''m -rf /'`처럼 문자열을 쪼개 붙이거나, base64로 인코딩해 두었다가 디코드해서 실행하거나, 인터프리터를 거치거나, 인자를 실행 중에 조립하는 식으로 회피 경로가 무한합니다. argv 패턴을 촘촘히 쌓아 이것을 막으려는 시도는 실패합니다. 그리고 실패한다는 사실을 감춘 채 사용자에게 보호를 약속하는 것이 더 나쁩니다.

실제 방어는 다른 두 곳에서 나옵니다.

- **자식 프로세스가 샌드박스를 그대로 물려받습니다.** `rm -rf /`가 실행되더라도 `file` 규칙이 허용하지 않은 경로는 지워지지 않습니다. 진짜 경계는 파일 규칙입니다.
- **egress 규칙이 반출을 막습니다.** 어떤 명령으로 시크릿을 읽어 냈든 내보낼 경로가 없습니다.

`argv` 조건의 가치는 다른 데 있습니다. 명백히 위험한 의도를 사람에게 미리 보여 주고(`ask`), 감사 로그에 굵은 흔적을 남기는 것입니다. 그 용도로만 씁니다.

곧 같은 `exec` 규칙 안에서도 두 축의 성질이 다릅니다. `program`은 커널이 강제하고, `argv_contains`와 `argv_pattern`은 중계 층이 관측할 뿐입니다. 강제 층은 argv 조건이 붙은 규칙을 프로파일로 옮기지 못한 규칙으로 보고합니다.

## 8. `egress` 규칙

```toml
[[rules]]
id = "gh-content"
kind = "egress"
host = "*.githubusercontent.com"
port = 443
action = "allow"
```

egress 규칙은 `host`, `port`, `protocol` 세 축으로 매칭합니다. 셋 다 규칙 쪽에서 생략할 수 있고, 생략한 축은 "무엇이든 매칭"입니다. 네 번째 필드 `max_bytes_out` 은 매칭 축이 아니라 **한도**이며 [8.4절](#84-max_bytes_out-총량-기반-차단)에서 다룹니다.

| 필드              | 필수  | 생략하면              | 값                                     |
|-----------------|-----|-------------------|---------------------------------------|
| `host`          | 예   |                   | 도메인 패턴, `*.접미사`, `*`, IP 리터럴           |
| `port`          | 아니오 | 모든 포트에 매칭         | 0-65535 정수 하나                         |
| `protocol`      | 아니오 | 모든 프로토콜에 매칭       | `tcp` \| `tls` \| `http`                |
| `max_bytes_out` | 아니오 | 총량 한도 없음          | 0 이상 정수. 이 세션에서 그 목적지로 반출할 수 있는 누적 바이트 |

### 8.1 `host`와 `port`

- `host`에는 도메인 패턴이나 IP 리터럴을 씁니다. `*.example.com`은 하위 도메인에만 매칭하고 `example.com` 자신에는 매칭하지 않으므로, 둘 다 원하면 규칙을 두 개 씁니다.
- `host = "*"`는 모든 호스트를 뜻하며, allowlist 정책의 맨 끝에 두는 차단 규칙으로 씁니다. `action = "allow"`와 함께 쓰면 로드를 거부합니다. 아웃바운드를 전부 여는 것은 `[defaults].egress = "allow"`와 실질적으로 같은데, 그것은 [2.2절](#22-defaults)이 문법 단계에서 막아 둔 설정이기 때문입니다.
- `port`를 생략하면 모든 포트에 적용됩니다.
- 정책 엔진은 비교 전에 호스트를 정규화합니다. 소문자로 바꾸고 후행 점을 지우는 것까지만 합니다. 정규화에 실패하면 어느 규칙에도 매칭시키지 않고 `[defaults]`로 보냅니다. 그리고 그 기본값은 `allow`가 될 수 없습니다([2.2절](#22-defaults)).
- v1은 IDN을 punycode로 바꾸지 않습니다. 비ASCII 호스트 패턴은 로드를 거부하므로, 국제화 도메인은 punycode(`xn--`) 형태로 직접 적어야 합니다. IDNA 처리기를 TCB에 넣지 않기 위한 선택입니다(`docs/design.md` 9.2). 관측된 호스트가 비ASCII이면 정규화 실패로 처리되어 `[defaults]`로 갑니다. 곧 특정 `deny` 규칙이 `[defaults].egress`보다 느슨해지는 일은 없습니다.
- 에이전트가 호스트명 없이 IP로 직접 연결하면 `host`는 IP 문자열이 됩니다. 도메인 패턴은 IP에 매칭되지 않습니다.
- IP는 canonical 형태로 정규화해 비교합니다. IPv4-mapped IPv6(`::ffff:1.2.3.4`)는 IPv4로 접어서 매칭하므로, 표기를 바꾸는 것만으로 IP 단위 deny를 빠져나갈 수 없습니다.

### 8.2 평문 아웃바운드 바닥

`protocol` 축은 관측 층이 그 연결에 대해 실제로 무엇을 보았는지를 뜻합니다.

| 값      | 뜻                                                    | 누가 방출하는가        |
|--------|------------------------------------------------------|-----------------|
| `tcp`  | 프로토콜을 모름. `connect(2)`만 봄                            | seccomp 중계 층    |
| `tls`  | CONNECT 터널. 포트와 무관하게 종단 간 암호화 요청                     | egress 프록시      |
| `http` | absolute-form 평문 요청. 프록시가 본문을 읽고 중계할 수 있음            | egress 프록시      |

`http`는 **본문이 프록시에게 그대로 보인다**는 뜻입니다. 곧 프록시와 목적지 사이 경로 어디에서든 같은 본문이 보입니다. 제로트러스트 게이트웨이가 이것을 정상 경로로 통과시키면 게이트웨이가 있으나 마나입니다.

그래서 정책 엔진은 4티어 평가가 끝난 뒤 평문 질의에 한해 **바닥(floor)** 을 한 번 더 씌웁니다. 판정은 정확히 아래 세 단계입니다.

1. [3절](#3-평가-의미론)의 0번부터 4번까지를 평소대로 돌려 `action`과 매칭된 규칙을 얻습니다.
2. 질의 프로토콜이 `http`이고 **매칭된 규칙이 `protocol`을 적지 않았다면**, `action`을 `[defaults].egress_plaintext`와 비교해 더 제한적인 쪽으로 내립니다. 아무 규칙도 매칭되지 않아 `[defaults].egress`가 답한 경우도 여기에 들어갑니다.
3. 매칭된 규칙이 `protocol = "http"`를 **명시적으로** 적었다면 바닥을 씌우지 않습니다. 사람이 평문인 줄 알고 연 것이므로 그 판단을 존중합니다.

`protocol = "tls"`나 `protocol = "tcp"`를 적은 규칙은 애초에 평문 질의에 매칭되지 않으므로 2번과 3번 어디에도 해당하지 않습니다. 곧 평문 질의에 매칭될 수 있는 규칙은 `protocol`이 없는 규칙과 `protocol = "http"`인 규칙 둘뿐입니다.

**왜 호스트만 적은 `allow`가 평문까지 열지 않는가.** 아래 규칙을 생각해 봅시다.

```toml
[[rules]]
id = "mirror"
kind = "egress"
host = "mirror.example.com"
action = "allow"
```

사용자가 적은 뜻은 "이 호스트와 통신해도 된다"이지 "이 호스트와 평문으로 통신해도 된다"가 아닙니다. 두 번째 뜻까지 자동으로 붙이면, 정책 파일 어디에도 평문을 열겠다고 적은 적이 없는데 평문이 열립니다. 평문을 열려면 사람이 `protocol = "http"`라고 직접 적어야 합니다.

바닥이 실제로 결정을 바꾼 경우, 그 사실은 합성 규칙 `airlock:egress-plaintext`로 감사 로그와 `airlock policy explain`에 나옵니다([12절](#12-airlock-policy-explain)). 원래 매칭된 규칙의 id는 그 표기 안에 그대로 남으므로 어떤 규칙이 평문을 열려다 막혔는지 추적할 수 있습니다. `airlock:egress-plaintext`는 예약 id이며 사용자 규칙이 같은 id를 쓰면 로드를 거부합니다.

`[defaults].egress_plaintext = "allow"`는 바닥을 없앱니다. `egress = "allow"`와 달리 로드를 거부하지는 않습니다. 이것이 여는 것은 "모든 호스트"가 아니라 "이미 허용된 호스트에 대한 평문"이라 범위가 훨씬 좁기 때문입니다. 다만 사람이 반드시 눈으로 보아야 하는 설정이므로 로드할 때 경고를 냅니다([10절](#10-로드-시-검증)).

### 8.3 강제 층과의 관계

`docs/design.md` 10.1절의 제약에 따라, 호스트 단위 강제는 egress 프록시 층이 있어야만 가능합니다. Landlock 백엔드는 포트까지만 강제합니다. 정책에 호스트 패턴이 있는데 프록시 층이 없으면 정책 엔진이 그 사실을 경고로 알립니다. 강제되지 않는 규칙을 강제되는 것처럼 보이게 두지 않습니다.

`protocol` 축도 마찬가지입니다. seccomp 중계 층은 `connect(2)`만 보므로 모든 연결을 `tcp`로 보고합니다(`docs/limitations.md` 5.12). 곧 `tls`와 `http`를 구분할 수 있는 것은 egress 프록시뿐입니다. 프록시 없이 도는 세션에서는 `protocol = "tls"`와 `protocol = "http"` 규칙이 아무것도 매칭하지 않고 평문 바닥도 발동하지 않으며, 반대로 `protocol = "tcp"` 규칙은 암호화된 연결까지 함께 잡습니다. 어느 쪽이든 사용자가 적은 뜻과 실제 판정이 어긋나므로, `protocol`을 적은 규칙 전부에 대해 정책 엔진이 로드할 때 경고를 냅니다.

프록시 층의 규격은 [`docs/egress-proxy.md`](./egress-proxy.md)입니다. 프록시를 켠 세션에서도 이 절의 문법과 의미는 하나도 바뀌지 않습니다. 호스트 문자열을 정책 엔진에 넘기는 주체가 중계 층에서 프록시로 바뀔 뿐이고, 정규화와 매칭 규칙은 그대로입니다. 다만 프록시가 있어도 해석된 IP를 되짚어 다시 판정하지는 않으므로 DNS 리바인딩은 여전히 이 어휘 밖입니다.

### 8.4 `max_bytes_out` 총량 기반 차단

```toml
[[rules]]
id = "mirror"
kind = "egress"
host = "mirror.example.com"
port = 443
protocol = "tls"
max_bytes_out = 10485760
action = "allow"
```

뜻은 하나입니다. **이 세션에서 그 목적지로 누적 반출한 바이트가 N 을 넘으면 그 규칙은 더 이상 허용하지 않습니다.**

- 누적량은 목적지 단위입니다. 키는 정규화된 호스트와 포트이며([8.1절](#81-host와-port)의 정규화를 그대로 씁니다), 표기를 바꾸는 것만으로 누적량이 초기화되지 않습니다.
- 누적량은 세션 안에서만 삽니다. 세션이 끝나면 0 부터 다시 셉니다. 세션을 넘는 한도는 이 어휘에 없습니다.
- 반출 바이트는 프록시 층이 실제로 중계한 페이로드입니다. TLS 레코드 오버헤드를 뺀 값이 아니고, 목적지에 완전히 써 넣은 조각만 셉니다.
- 초과 시 결정은 **`deny` 로 고정**됩니다. `ask` 로 두면 `--yes` 자동 승인이 한도를 그대로 무력화하기 때문입니다. 규칙 자신이 `ask` 였더라도 한도를 넘은 뒤에는 묻지 않고 막습니다.
- 이미 막는 규칙(`action = "deny"`)에 `max_bytes_out` 을 적으면 로드를 거부합니다. 한도는 통과시키는 규칙에만 뜻이 있고, 적어 두면 총량 제한이 걸렸다고 잘못 믿게 됩니다.

**한도를 넘긴 그 연결 자체는 막지 못합니다.** 바이트 수는 연결이 끝나야 알 수 있으므로 판정은 언제나 **연결 시작 시점**에 이미 아는 누적량으로 합니다. 곧 순서는 이렇습니다.

1. 연결을 시작할 때 누적량이 한도 이하이면 통과시킵니다.
2. 그 연결이 얼마를 반출하든 중간에 끊지 않습니다.
3. 연결이 끝나면 그만큼을 누적에 더합니다.
4. **다음 연결부터** 막힙니다.

`max_bytes_out = 10485760` 이라고 적었는데 한 연결이 1GiB 를 반출했다면 그 1GiB 는 나갑니다. 막히는 것은 그다음 연결입니다. 이것은 구현의 미비가 아니라 TLS 를 종단하지 않는 v1 에서 총량으로 할 수 있는 것의 경계입니다. "차단" 이라고 쓰고 실제로는 사후에만 막힌다면 그건 거짓 보증이므로 여기에 그대로 적습니다. 연결 도중에 끊으려면 프록시가 스트림을 세면서 한도에서 잘라야 하고, 그것은 [`docs/egress-proxy.md` 5절](./egress-proxy.md)의 내용 검사기가 붙는 자리입니다.

한도가 결정을 바꾼 경우, 그 사실은 합성 규칙 `airlock:egress-quota` 로 감사 로그와 `airlock policy explain` 에 나옵니다. 매칭 표기에 한도와 실제 누적량과 원래 규칙 id 가 함께 남으므로, 무엇이 얼마를 넘겨서 막혔는지 로그만 보고 알 수 있습니다.

```
결정     deny
규칙     airlock:egress-quota (baseline tier)
매칭     mirror.example.com:443 [max_bytes_out=10485760 used=12000000] <- mirror
```

`max_bytes_out` 은 **프록시가 있어야 의미가 있습니다.** 반출 바이트를 세는 층은 프록시뿐이고, 중계 층은 `connect(2)` 만 보므로 누적량이 늘 0 입니다. 곧 `airlock run --egress-proxy` 없이 도는 세션에서는 한도가 한 번도 걸리지 않으며, 정책 엔진이 로드할 때 그 사실을 경고로 알립니다.

## 9. 내장 베이스라인

`airlock-policy`에 컴파일되어 들어가는 규칙입니다. 사용자 정책 파일이 없어도 항상 적용됩니다.

`forbid`로 두는 것은 다음과 같습니다. [3.2절](#32-forbid와-overrides)에 따라 `overrides`로 지목해야만 예외를 둘 수 있습니다.

| id                   | 대상                                                                               | 근거                      |
|----------------------|----------------------------------------------------------------------------------|-------------------------|
| `ssh-private-keys`   | `~/.ssh/**`                                                                      | SSH 개인키와 known_hosts    |
| `aws-credentials`    | `~/.aws/**`                                                                      | 클라우드 자격증명               |
| `gcloud-credentials` | `~/.config/gcloud/**`                                                            | 클라우드 자격증명               |
| `kube-config`        | `~/.kube/**`                                                                     | 클러스터 관리자 자격증명           |
| `gpg-keyring`        | `~/.gnupg/**`                                                                    | 서명/복호화 키                |
| `env-files`          | `**/.env`, `**/.env.*`                                                           | 애플리케이션 시크릿              |
| `netrc`              | `~/.netrc`, `~/_netrc`                                                           | 평문 자격증명                 |
| `registry-tokens`    | `~/.npmrc`, `~/.pypirc`, `~/.cargo/credentials{,.toml}`, `~/.docker/config.json` | 패키지 레지스트리 토큰. 공급망 공격 경로 |
| `shell-history`      | `~/.bash_history`, `~/.zsh_history`, `~/.python_history`, `~/.psql_history` 등    | 과거 명령에 섞인 시크릿           |
| `system-credentials` | `/etc/shadow`, `/etc/sudoers`, `/etc/sudoers.d/**`                               | 시스템 자격증명                |
| `browser-profiles`   | Chrome/Chromium/Brave/Edge/Firefox/Safari 프로필과 쿠키 DB (macOS/Linux 경로)            | 세션 탈취                   |

`~/.ssh/**` 전체를 forbid로 두므로 `authorized_keys` 쓰기도 자동으로 함께 막힙니다. 같은 대상을 더 약한 `ask` 규칙으로 한 번 더 적는 것은 중복이고, 둘이 어긋날 여지만 만듭니다.

`ask`로 두는 것은 다음과 같습니다.

| id                   | kind | 대상                                                                                                           |
|----------------------|------|--------------------------------------------------------------------------------------------------------------|
| `shell-init-write`   | file | `~/.bashrc`, `~/.bash_profile`, `~/.zshrc`, `~/.zshenv`, `~/.zprofile`, `~/.profile`, `~/.config/fish/**` 쓰기 |
| `git-config-write`   | file | `~/.gitconfig`, `~/.config/git/config` 쓰기. `core.pager` 등으로 코드 실행이 가능함                                       |
| `autostart-write`    | file | `~/Library/LaunchAgents/**`, `~/.config/systemd/user/**`, `~/.config/autostart/**`, `/etc/cron.d/**` 쓰기      |
| `danger-rm`          | exec | `rm` + `-rf`                                                                                                 |
| `sudo-exec`          | exec | `sudo`                                                                                                       |
| `doas-exec`          | exec | `doas`                                                                                                       |
| `crontab-exec`       | exec | `crontab`                                                                                                    |
| `pipe-curl-to-shell` | exec | argv에 `curl ... \| ...sh` 형태가 보임                                                                             |
| `pipe-wget-to-shell` | exec | argv에 `wget ... \| ...sh` 형태가 보임                                                                             |

`shell-init-write`와 `autostart-write`, `crontab-exec`가 베이스라인에 있는 이유는 위협 모델 3.2의 1번(프롬프트 인젝션)과 이어집니다. 인젝션에 성공한 공격자의 다음 수순은 거의 항상 지속성 확보이며, 한 번의 인젝션을 영구적인 접근으로 바꾸는 경로를 기본으로 열어 두지 않겠다는 뜻입니다.

`forbid` 규칙은 전부 [3.3절의 probe 경로](#33-효력-없는-예외-규칙-찾아내기)를 함께 정의합니다. probe가 없는 `forbid`는 효력 없는 예외 규칙을 검사할 수 없으므로, 구현에서 테스트로 강제합니다.

## 10. 로드 시 검증

정책 엔진은 아래를 모두 통과해야 로드에 성공합니다. 하나라도 실패하면 **정책을 적용하지 않고 실행 자체를 중단합니다.** 깨진 정책을 무시하고 실행을 이어 가는 것은 fail-open이기 때문입니다.

1. `version`이 1입니다.
2. TOML 문법이 유효하고, 정책 엔진이 모르는 키가 없습니다.
3. `id`가 유일합니다. 사용자 규칙끼리 겹치지 않는 것은 물론이고 내장 베이스라인·자기보호 규칙의 id와도 겹치지 않아야 합니다. 감사 로그의 `rule` 필드에는 티어가 담기지 않으므로, id가 겹치면 그 결정을 낸 규칙이 어느 티어의 것인지 로그만 보고는 알 수 없게 됩니다. `overrides`로 내장 id를 **지목**하는 것은 이것과 별개이며 정상입니다.
3-1. `id`가 `airlock:` 으로 시작하지 않습니다. 그 접두는 정책 엔진과 브로커가 만드는 합성 규칙(`airlock:egress-plaintext`, `airlock:egress-quota`, `airlock:egress-proxy`, `airlock:egress-summary`) 전용 이름 공간입니다. 사용자 규칙이 같은 이름을 쓰면 감사 로그의 `rule` 필드만 보고 그 결정이 엔진이 씌운 바닥인지 사람이 적은 규칙인지 알 수 없어집니다. 개별 id 를 하나씩 예약하지 않고 접두를 통째로 막는 이유는, 나중에 늘어나는 합성 id 하나를 예약 목록에 넣는 것을 잊어도 그 이름을 가져갈 수 없게 하기 위함입니다.
3-2. `id`가 영숫자와 `.` `_` `-` `:` 로만 되어 있습니다. id는 macOS 커널 프로파일에 주석으로 그대로 들어갑니다. 여기에 개행이 섞이면 주석이 그 자리에서 끝나고 뒷부분이 살아 있는 SBPL 지시문이 됩니다. SBPL은 마지막 규칙이 이기는 언어라, 그 자리에 넓은 `allow` 하나를 심으면 베이스라인 forbid까지 덮입니다. 브로커도 프로파일을 내보낼 때 제어 문자를 한 번 더 지우지만, 정책 엔진이 로드 시점에서 먼저 거부합니다.
4. 모든 `action`과 `kind`, `mode`, `protocol` 값이 정책 엔진이 아는 값입니다. `protocol`은 `tcp`, `tls`, `http` 셋뿐입니다.
5. 모든 `path` 패턴이 [5절](#5-glob-문법) 문법에 맞고 절대 경로입니다.
6. `[defaults].egress`가 `allow`가 아닙니다. 네 기본값 어디에도 `forbid`가 없습니다.
7. `overrides`가 존재하는 내장 `forbid` id를 지목하고, `reason`이 비어 있지 않습니다.
8. `kind`에 맞지 않는 필드가 없습니다 (예: `file` 규칙에 `port`나 `protocol`이나 `max_bytes_out`).
9. `max_bytes_out`이 막는 규칙(`action = "deny"`)에 붙어 있지 않습니다 ([8.4절](#84-max_bytes_out-총량-기반-차단)).

아래는 경고만 내고 로드는 성공시킵니다.

- [3.3절](#33-효력-없는-예외-규칙-찾아내기)의 probe 검사에 걸린, 효력 없는 예외 규칙
- 앞선 규칙에 완전히 가려져 영원히 매칭되지 않는 규칙
- 커널 강제 백엔드가 표현할 수 없는 규칙 ([8.1절](#81-host와-port)의 호스트 패턴·IP 리터럴에 프록시 층이 없는 경우)
- `protocol`을 적은 규칙 ([8.3절](#83-강제-층과의-관계)). 프록시 없이 도는 세션에서는 아무것도 매칭하지 않습니다
- `max_bytes_out`을 적은 규칙 ([8.4절](#84-max_bytes_out-총량-기반-차단)). 프록시 없이 도는 세션에서는 누적량이 늘 0 이라 한도가 한 번도 걸리지 않습니다
- `[defaults].egress_plaintext = "allow"` ([8.2절](#82-평문-아웃바운드-바닥)). 평문 바닥을 없애는 설정입니다
- 한 번도 쓰이지 않은 `overrides`

뒤의 두 항목은 판정 기준을 아래처럼 고정합니다.

**"영원히 매칭되지 않는 규칙" 판정.** [3.3절](#33-효력-없는-예외-규칙-찾아내기)과 같은 이유로 패턴 대수 대신 대표 경로를 씁니다. 검사할 규칙의 각 패턴에서 대표 경로를 하나씩 뽑고, 그 규칙이 가진 **모든** 패턴과 **모든** 모드의 조합을 앞선 규칙들이 빠짐없이 덮을 때만 경고합니다. 하나라도 덮이지 않으면 그 규칙은 여전히 쓸모가 있으므로 경고하지 않습니다. 일부만 덮여도 경고하게 만들면, 좁은 규칙을 앞에 두고 넓은 규칙을 뒤에 두는 지극히 정상적인 정책이 전부 오탐이 됩니다. 조용히 무효한 규칙만큼이나 조용히 무시되는 경고도 나쁩니다.

**"쓰이지 않은 `overrides`" 판정.** 그 사용자 규칙 자신이 닿는 범위가 지목한 `forbid` 규칙의 범위와 겹치는지로 판정합니다. `forbid`의 probe 경로를 기준으로 판정하지 않는 이유는, [3.2절의 `read-ssh-config`](#32-forbid와-overrides) 예제처럼 probe를 비껴가면서도 실제로는 예외가 성립하는 정당한 규칙이 "쓰이지 않았다"고 잘못 보고되기 때문입니다.

## 11. 정책 다이제스트

감사 로그의 제네시스(genesis) 엔트리에 들어가는 값입니다(`docs/audit-format.md` 5.1).

```
policy_digest = SHA-256("airlock.policy.v2\x00" || canonical(정규화된 규칙 집합))
```

도메인 문자열의 `v2`는 정책 **파일**의 `version`과 다른 축입니다. 파일 형식은 여전히 `version = 1`이고, 바뀐 것은 정규 인코딩의 스키마입니다. `protocol` 축과 `[defaults].egress_plaintext`와 `max_bytes_out`이 인코딩에 들어가면서 같은 정책 파일이 v1과 다른 값을 내게 되었으므로 도메인을 함께 올렸습니다. 같은 도메인 안에서 인코딩만 조용히 바꾸면 옛 다이제스트와 위조된 다이제스트를 구분할 수 없습니다(`docs/limitations.md` 7.9).

다이제스트는 원본 TOML 텍스트가 아니라 **정규화된 규칙 집합**에 대해 계산합니다. 주석과 공백, 키 순서가 바뀌어도 실제 효력이 같으면 같은 값이 나와야 합니다. 반대로 규칙 하나의 `action`, `path`, `reason`이 바뀌거나 규칙의 **순서**가 바뀌면 반드시 달라져야 합니다. [3절](#3-평가-의미론)에서 보았듯 순서가 결과를 바꾸기 때문입니다.

정규화 인코딩은 [`docs/audit-format.md` 6.1](./audit-format.md#61-기본-요소)의 길이 접두 방식을 그대로 씁니다. 이 목적으로 `airlock-canonical` 크레이트를 감사 층과 공유합니다.

무엇을 어떤 형태로 넣을지는 아래처럼 고정합니다. 목적은 다이제스트가 **머신에 종속되지 않게** 하는 것입니다. 같은 정책 파일이 머신마다 다른 다이제스트를 내면 정책 비교도 배포 검증도 불가능해집니다.

| 대상           | 인코딩                                   |
|--------------|---------------------------------------|
| 티어 0 자기보호 규칙 | 구체 경로가 아니라 버전 표식 문자열 `selfprotect.v1` |
| `[defaults]` | `file`, `exec`, `egress`, `egress_plaintext` 네 action 태그 |
| 사용자 규칙       | 선언 순서대로 전부                            |
| 내장 베이스라인 규칙  | 정의 순서대로 전부                            |
| 경로 패턴        | **작성된 그대로**. `~`를 펼치지 않음              |
| egress `protocol` | 없으면 부재 표식, 있으면 프로토콜 태그 (`tcp` 1, `tls` 3, `http` 4) |
| egress `max_bytes_out` | 없으면 부재 표식, 있으면 그 정수. `protocol` 다음 자리 |

티어 0을 경로로 인코딩하지 않는 이유는 감사 디렉토리와 바이너리 경로가 설치마다 다르기 때문입니다. 대신 버전 표식을 넣어, 자기보호 계약이 바뀌면 다이제스트도 바뀌게 했습니다. 경로 패턴을 `~` 확장 전 형태로 인코딩하는 이유도 같습니다. `~/.ssh/**`는 어느 머신에서든 같은 규칙입니다.

## 12. `airlock policy explain`

[1절](#1-설계-원칙)의 "실행 없이 답할 수 있어야 한다"를 사용자에게 그대로 노출하는 명령입니다. 에이전트를 돌리지 않고도 특정 경로에 어떤 결정이 나는지 물어볼 수 있습니다.

```bash
$ airlock policy explain --file ~/.ssh/config --mode read
# 요청     /Users/me/.ssh/config
# 해소     /Users/me/.ssh/config
# 모드     read
# 결정     forbid
# 규칙     ssh-private-keys (baseline tier)
# 매칭     ~/.ssh/**
# 근거     SSH 개인키와 known_hosts
```

`--host`로 물을 때는 `--protocol`로 프로토콜을 함께 넘깁니다. 평문 바닥이 결정을 바꾼 경우 규칙 자리에 합성 규칙이 나오고, 원래 매칭된 규칙의 id가 매칭 표기 안에 남습니다.

```bash
$ airlock policy explain --host mirror.example.com --port 80 --protocol http
# 호스트   mirror.example.com
# 포트     80
# 프로토콜 http
# 결정     deny
# 규칙     airlock:egress-plaintext (baseline tier)
# 매칭     mirror.example.com:80 [http] <- mirror
# 근거     평문 아웃바운드는 [defaults].egress_plaintext 가 정한 바닥을 넘지 못함. 열려면 그 규칙에 protocol = "http" 를 명시할 것
```

무엇이 왜 막혔는지 즉시 답하지 못하는 정책 엔진은 false positive를 튜닝할 방법이 없고, 그러면 `docs/design.md` 8장이 지목한 "개발자 짜증" 리스크를 그대로 방치하게 됩니다.

## 13. 테스트 의무

### 평가 의미론

- 티어 0 규칙이 사용자 `allow`보다 우선함
- 티어 0 규칙은 `overrides`로도 열리지 않음
- 사용자 규칙은 선언 순서대로 보고 처음 매칭된 것이 답함
- 매칭되는 규칙이 없으면 `[defaults]`가 답함
- `ask`에 응답이 없는 경우와 tty가 없는 경우가 모두 거부로 귀결됨

### 로드 검증

- [9절](#9-내장-베이스라인)의 모든 `forbid` probe에 대해, `overrides` 없는 사용자 `allow`는 실제 결정을 바꾸지 못하고 경고만 냄
- 넓은 작업 공간 `allow` 규칙이 그 안의 `.env`와 `~/.ssh`를 열지 못함 ([3.0절](#30-왜-forbid가-사용자-규칙보다-위인가))
- `overrides`가 있는데 `reason`이 빈 문자열이면 로드 실패
- 모르는 키, 오타 난 `action`, 상대 경로 패턴, `a**b` 패턴이 각각 로드 실패
- `[defaults].egress = "allow"`가 로드 실패
- `[defaults]`의 세 kind 어디든 `forbid`면 로드 실패 ([2.2절](#22-defaults))
- 사용자 규칙의 `action = "forbid"`가 로드 실패 ([2.1절](#21-공통-필드))
- 겹치는 `forbid` 중 하나만 `overrides`로 지목했을 때, 지목하지 않은 나머지는 계속 우선함 ([3.2절](#32-forbid와-overrides))

### 경로 정규화 (적대적)

각 항목은 시크릿에 닿으려는 실제 우회 시도이며, 전부 `deny`가 나와야 합니다.

- `~/.ssh/../.ssh/id_rsa`
- `~/work/../.ssh/id_rsa`
- `/Users/me/./.ssh//id_rsa`
- `~/.ssh/./id_rsa`
- `/tmp/link -> ~/.ssh` 후 `/tmp/link/id_rsa`
- `/tmp/a/b` 중 `a`가 `~/.ssh`로의 링크인 중간 세그먼트 링크
- `~/.SSH/id_rsa`, `~/.Ssh/id_rsa` ([4.3절](#43-대소문자와-유니코드) 대소문자)
- `~/작업/*.pem`이 `deny`일 때 NFD로 표기한 `~/작업/키.pem` ([4.3절](#43-대소문자와-유니코드) 정규화)
- `link -> ~/.ssh` 후 `link/../.ssh/id_rsa` (커널은 링크를 먼저 따르고 `..`를 나중에 적용)
- 루트 위로 올라가는 `../../../../etc/shadow`
- 존재하지 않는 경로를 포함한 `~/.ssh/nonexistent/../id_rsa`
- `~/work/dir -> ~/.ssh/sub`, `~/.ssh/sub/x -> ../id_rsa` 후 `~/work/dir/x` (상대 링크 대상은 해소된 부모에 붙임). 대상이 아직 없는 `~/.ssh/sub/ak -> ../authorized_keys`도 같은 결과여야 함
- macOS 한정. `/System/Volumes/Data/<홈>/.ssh/id_rsa`가 `~/.ssh/**`에 걸리고, Data 표기로 등록한 자기보호 후보와 Data 표기로 적은 사용자 규칙이 루트 표기 요청과 하나로 수렴함

반대 방향으로, `allow` 규칙이 대소문자나 정규화 변형 때문에 넓어지지 않는지 확인합니다.

- `~/work/proj/**`가 `allow`일 때 `~/WORK/proj/x`는 `allow`가 아님
- `~/작업/**`가 `allow`일 때 NFD로 표기한 `~/작업/x`는 `allow`가 아님

### glob 매처

- `*`가 `/`를 넘지 않음
- `**`가 0개 세그먼트에 매칭 (`a/**`가 `a`에 매칭)
- `**/.env*`가 임의 깊이의 `.env`, `.env.local`에 매칭
- `?`가 정확히 한 바이트이며 `/`를 넘지 않음

### egress

- `*.example.com`이 `a.example.com`에 매칭하고 `example.com`에는 매칭하지 않음
- `EXAMPLE.com.`이 `example.com`으로 정규화됨
- 도메인 패턴이 IP 리터럴에 매칭하지 않음
- 비ASCII 호스트 패턴이 로드 거부됨
- IPv4-mapped IPv6(`::ffff:1.2.3.4`)이 IPv4로 접혀 IP 단위 deny를 빠져나가지 못함

### 평문 바닥 ([8.2절](#82-평문-아웃바운드-바닥))

- 호스트만 적은 `allow` 규칙이 있을 때 같은 호스트로의 `http` 질의가 거부됨 (핵심 회귀)
- 같은 규칙으로 `tls` 질의는 허용됨
- `protocol = "http"`를 명시한 `allow` 규칙은 `http` 질의를 통과시킴
- `protocol = "tls"`를 적은 규칙이 `http` 질의에 매칭되지 않음
- `[defaults].egress_plaintext = "allow"`가 경고를 내되 로드는 성공함
- `[defaults].egress_plaintext = "forbid"`가 로드 실패함
- `protocol`을 적은 규칙이 프록시 필요 경고를 냄
- `kind = "file"`이나 `kind = "exec"` 규칙에 `protocol`을 쓰면 로드 실패함
- 알 수 없는 `protocol` 값이 로드 실패함
- `Protocol` 태그가 감사 층의 태그와 같음 (`tcp` 1, `tls` 3, `http` 4)

### 다이제스트

- 주석과 공백, 규칙 필드 순서만 다른 두 정책의 다이제스트가 같음
- `action` 하나만 다른 두 정책의 다이제스트가 다름
- 규칙 순서가 다르면 다이제스트가 다름 (순서가 결과를 바꾸므로)
- `protocol`만 다른 두 정책의 다이제스트가 다름
- `[defaults].egress_plaintext`만 다른 두 정책의 다이제스트가 다름
