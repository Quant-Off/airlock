# 정책 DSL 규격 (airlock.policy.v1)

`airlock-policy`가 구현하는 capability 정책의 문법과 평가 의미론입니다. 구현과 이 문서가 어긋나면 이 문서가 정본입니다.

## 1. 설계 원칙

- **결정 가능성**: 정책은 튜링 완전하지 않습니다. "이 정책이 이 경로에 무엇을 하는가"를 실행 없이 정적으로 답할 수 있어야 하며, `airlock policy explain`이 이 성질에 의존합니다.
- **실패는 제한 방향으로**: 모호한 상황에서는 항상 더 좁은 결정을 냅니다. 파싱 실패는 fail-open이 아니라 로드 거부입니다.
- **완화는 명시적으로**: 시크릿 보호를 푸는 것은 가능하지만, 근거 없이는 파일이 로드되지 않습니다.
- **암묵적 신뢰 없음**: 매칭되는 규칙이 없으면 `[defaults]`가 답하고, 그 기본값도 `allow`가 될 수 없는 항목이 있습니다.

## 2. 파일 구조

```toml
version = 1
name = "claude-code-default"

[defaults]
file   = "ask"
exec   = "ask"
egress = "deny"

[[rules]]
id     = "workspace-rw"
kind   = "file"
path   = "~/work/airlock/**"
mode   = ["read", "write", "create", "delete"]
action = "allow"

[[rules]]
id     = "env-files"
kind   = "file"
path   = "**/.env*"
action = "deny"
reason = "환경 변수 시크릿"

[[rules]]
id     = "danger-rm"
kind   = "exec"
program = "rm"
argv_contains = ["-rf"]
action = "ask"

[[rules]]
id     = "llm-endpoint"
kind   = "egress"
host   = "api.anthropic.com"
port   = 443
action = "allow"
```

### 2.1 공통 필드

| 필드          | 필수  | 설명                                                                                                   |
|-------------|-----|------------------------------------------------------------------------------------------------------|
| `id`        | 예   | 영숫자와 `.` `_` `-` `:` 만 쓸 수 있음. 파일 내에서 유일하고 내장 규칙 id와 겹치지 않을 것. 감사 로그의 `rule` 필드에 기록되므로 안정적인 이름을 쓸 것    |
| `kind`      | 예   | `file` \| `exec` \| `egress`                                                                         |
| `action`    | 예   | `allow` \| `deny` \| `ask`. `forbid`는 내장 베이스라인 전용이며 사용자 규칙에 쓰면 로드 거부 ([3.2절](#32-forbid와-overrides)) |
| `reason`    | 조건부 | 사람이 읽는 근거. `overrides`를 쓸 때 필수                                                                       |
| `overrides` | 아니오 | 완화하려는 내장 `forbid` 규칙의 id                                                                             |

알 수 없는 키는 **로드 거부**이며 무시하지 않습니다. 오타 난 `mode` 키를 조용히 무시하면 의도보다 넓은 규칙이 조용히 활성화됩니다.

### 2.2 `[defaults]`

`file`과 `exec`은 `allow` \| `deny` \| `ask` 중 하나입니다. `egress`는 `allow`를 쓸 수 없습니다. 아웃바운드 기본 허용은 데이터 반출([위협 모델 3.2](./design.md#32-공격자와-위협)의 5번)에 대한 방어를 통째로 포기하는 설정이므로 문법 수준에서 막습니다.

## 3. 평가 의미론

결정은 아래 순서로 내려갑니다. 이를 티어(tier)라고 하며, 먼저 매칭된 곳에서 멈춥니다.

```
0. 자기보호 규칙           (주입됨, 표현 불가, 완화 불가)
1. 내장 forbid 규칙       (overrides 로 지목한 사용자 규칙만 이길 수 있다)
2. 사용자 규칙             (선언 순서, 첫 매칭 승)
3. 내장 ask/deny 규칙     (정의 순서, 첫 매칭 승. 사용자 규칙이 덮을 수 있다)
4. [defaults]           (kind별 기본값)
```

첫 매칭 승(first-match-wins)을 택한 이유는 예측 가능성입니다. "가장 구체적인 규칙 승" 방식은 구체성 비교 규칙 자체가 미묘한 버그의 온상이고, 사용자가 자기 정책을 읽고 결과를 예측하기 어렵게 만듭니다. 선언 순서는 위에서 아래로 읽으면 끝입니다.

### 3.0 왜 forbid가 사용자 규칙보다 위인가

처음엔 티어가 자기보호 -> 사용자 -> 베이스라인 순서였습니다. 그러면 가장 흔하고 가장 정당한 규칙 하나가 시크릿 보호를 통째로 무력화합니다.

```toml
[[rules]]
id = "workspace"
kind = "file"
path = "~/work/**"
action = "allow"
```

이 규칙이 베이스라인보다 먼저 매칭되므로 `~/work/api/.env`도 허용됩니다. 사용자는 "내 작업 공간을 열었다"고만 생각했는데 실제로는 애플리케이션 시크릿 보호를 껐습니다.

이를 로드 시점 오류로 막으면 더 나빠집니다. 작업 공간을 허용하는 모든 정책이 `overrides = "env-files"`를 요구받게 되고, 사용자는 의미를 따지지 않고 관성적으로 override를 붙이는 습관을 들이며, 방어가 형식으로 전락합니다.

그래서 `forbid`를 사용자 규칙 위로 올렸습니다. 결과는 두 가지입니다.

- 넓은 allow 규칙이 시크릿을 열지 못합니다. 위 `workspace` 규칙은 그대로 두고 쓰면 되고, `.env`와 `~/.ssh`는 계속 막힙니다.
- 완화는 `overrides`로 대상을 지목할 때만 효력이 생깁니다. 곧 "시크릿 기본 deny, 완화는 명시적 근거로만"이 heuristic 검사가 아니라 평가 구조 자체로 보장됩니다.

### 3.1 자기보호 규칙 (티어 0)

브로커가 주입하며 DSL로 표현할 수도, 끌 수도, 완화할 수도 없습니다. `overrides`로도 뚫리지 않습니다.

| 대상                                            | 결정     |
|-----------------------------------------------|--------|
| 감사 디렉토리 (`chain.jsonl`, `head.json`) 쓰기/생성/삭제 | `deny` |
| 활성 정책 파일 쓰기/생성/삭제                             | `deny` |
| Airlock 바이너리 자신 쓰기/생성/삭제                      | `deny` |

감사 로그가 자기를 기록하는 대상에게 쓰기 가능하면 그 로그는 증거가 아니고, 정책 파일이 피보호 프로세스에게 쓰기 가능하면 그 정책은 강제가 아닙니다. 이 두 규칙은 협상 대상이 아니므로 정책 언어 밖에 둡니다.

감사 디렉토리 **읽기**는 티어 0에서 다루지 않습니다. 사용자가 자기 로그를 에이전트에게 보여 주고 싶은 정당한 경우가 있으므로 이러한 점을 완화 가능해야 하고, 티어 0은 그것이 불가하기 때문입니다.

읽기는 베이스라인에도 넣지 않고 `[defaults].file`로 떨어뜨립니다. 기본값이 `ask`이므로 조용히 통과하지 않습니다. 베이스라인에 중복 규칙을 두지 않는 이유는 두 가지입니다. 첫째로 같은 대상을 두 티어에서 규정하면 언젠가 갈라지고 어느 쪽이 진짜인지 모르게 되며, 둘째로 베이스라인 규칙은 11절의 다이제스트에 들어가는데 감사 경로는 머신마다 다르므로 넣으면 다이제스트가 머신 종속이 되어 정책 비교가 불가능해집니다.

### 3.2 `forbid`와 `overrides`

`forbid`는 "완화하려면 명시적으로 이 규칙을 지목하라"는 뜻의 `deny`이며, 내장 베이스라인에서만 쓰입니다.

`forbid`가 매칭되면 평가는 그 자리에서 멈추지 않고 한 가지만 더 확인합니다. 같은 요청에 매칭되고 그 `forbid` 규칙의 id를 `overrides`로 지목한 사용자 규칙이 있는지를 보고, 있으면 그 사용자 규칙이 우선되고 없으면 `forbid`가 우선됩니다.

완화 규칙은 아래를 모두 만족해야 하며, 하나라도 어기면 로드가 실패합니다.

```toml
[[rules]]
id        = "read-ssh-config"
kind      = "file"
path      = "~/.ssh/config"
mode      = ["read"]
action    = "allow"
overrides = "ssh-private-keys"
reason    = "배포 대상 호스트 별칭을 읽어야 함. 개인키는 별도 forbid로 유지"
```

- `overrides`가 실제 존재하는 내장 `forbid` 규칙 id를 지목합니다.
- `reason`이 비어 있지 않습니다.

이 두 조건이 만족되면 완화가 감사 로그의 정책 다이제스트에 그대로 남습니다. 곧 "누가 언제 어떤 근거로 시크릿 보호를 풀었는가"가 사후에 증명됩니다.

##### 커널 프로파일 한계

현재 macOS Seatbelt 프로파일은 override 완화를 반영하지 않습니다. SBPL(Seatbelt Policy Language)은 "이 forbid에서 이 부분집합만 제외"라는 교집합을 표현할 수 없고, 완화 규칙의 패턴을 deny 뒤에 통째로 allow로 내보내면 같은 경로에 겹치는 다른 forbid까지 뚫리기 때문입니다. 그래서 커널은 완화된 경로도 여전히 차단합니다. 정책 계층보다 커널이 더 좁은 fail-closed 방향이며, 이 gap은 `airlock run` 배너와 enforcer의 gap 목록에 스스로 표시됩니다.

### 3.3 무효한 완화 탐지

3.0절의 티어 순서 덕분에 근거 없는 완화는 **보안 문제가 아니라 무효한 규칙**이 됩니다. 문제는 사용자가 자기 규칙이 아무 일도 하지 않는다는 사실을 모른다는 것이며, 조용히 무효한 규칙은 조용히 뚫리는 규칙만큼 나쁩니다.

그래서 로드 시점에 이를 찾아 경고합니다. 패턴 교집합을 일반적으로 계산하지는 않고, 각 내장 `forbid` 규칙이 자신을 대표하는 **구체 probe 경로 집합**을 함께 정의합니다.

```
ssh-private-keys  probes: ~/.ssh/id_rsa, ~/.ssh/id_ed25519, ~/.ssh/identity
aws-credentials   probes: ~/.aws/credentials, ~/.aws/config
env-files         probes: ~/proj/.env, ~/proj/api/.env.production
```

로드 시점에 각 probe 경로를 모든 파일 모드에 대해 사용자 규칙만으로 평가합니다. 결과가 `allow` 또는 `ask`인데 그 규칙에 해당 `forbid`를 지목한 `overrides`가 없으면 경고를 발생시킵니다. 로드는 성공하며, 실제 결정은 `forbid`이므로 안전합니다.

패턴 대수 대신 구체 probe를 쓰는 이유는 판정이 실행 가능하고 테스트 가능하기 때문입니다. probe 목록이 곧 "우리가 반드시 막겠다고 약속한 것"의 명세가 됩니다. 구현은 모든 `forbid` 규칙이 probe를 하나 이상 갖는지, 그리고 각 probe가 자기 규칙에 실제로 매칭되는지를 테스트로 강제합니다.

### 3.4 결정 결과

| 결정       | 브로커 동작                                                                        |
|----------|-------------------------------------------------------------------------------|
| `allow`  | 허용. 감사 엔트리 기록                                                                 |
| `deny`   | 거부. 감사 엔트리 기록. 피보호 프로세스에는 권한 오류로 보임 (macOS Seatbelt는 `EPERM`)                 |
| `ask`    | 감사 엔트리(`ask`) 기록 -> `/dev/tty`로 승인 요청 -> `approval` 엔트리 기록 -> 그 결과대로 허용 또는 거부 |
| `forbid` | `deny`와 동일하게 동작. 구분은 로드 시점 의미론에만 있음                                           |

`ask`에 응답이 없거나 제어 터미널이 없으면 **거부**합니다. 승인 채널이 없을 때 통과시키면 `ask`가 `allow`로 조용히 격하됩니다.

예외는 `airlock run --yes` 하나뿐입니다. 모든 `ask`를 사람 확인 없이 승인하며, 승인 통제를 포기하는 설정이므로 시작 시 경고를 내고 각 `approval` 엔트리에 자동 승인이었다는 note를 남깁니다. 조용한 격하와 다른 점은 사용자가 명시적으로 켰고 그 사실이 감사 로그에 남는다는 것입니다.

승인 프롬프트에 들어가는 값은 표시 전에 제어 문자와 양방향 재정렬 문자를 눈에 보이는 형태로 바꿉니다. 경로와 argv는 신뢰할 수 없는 입력이고, 이스케이프 시퀀스가 그대로 나가면 에이전트가 승인 화면을 다시 그려 위조할 수 있기 때문입니다([`docs/design.md` 9.4](design.md#94-ask-승인-ux-devtty-직결-인라인-프롬프트)).

## 4. 경로 정규화

여기가 실제 우회가 발생하는 지점입니다. 매칭 전에 아래를 순서대로 적용합니다.

1. `~`를 홈 디렉토리로 확장합니다. `~user` 형태는 v1에서 지원하지 않고 로드 거부입니다.
2. 상대 경로면 해당 시점의 cwd 기준으로 절대화합니다.
3. **요청 경로**: `.`과 빈 세그먼트를 제거하고 `..`를 어휘적으로 해소합니다. 루트 위로 올라가는 `..`는 루트에서 흡수합니다.
4. **해소 경로**: 어휘 정리 **전**의 절대 경로에서 심볼릭 링크를 해소한 뒤 어휘 정리를 적용합니다. 커널은 링크를 먼저 따라간 다음 `..`를 적용하므로, `..`를 먼저 어휘적으로 지우면 `link/..` 형태가 커널과 다른 곳을 가리키게 됩니다. 경로가 존재하면 실제 해소를 시도하고, 존재하지 않으면 존재하는 최장 접두를 해소한 뒤 나머지를 어휘적으로 붙입니다.

### 4.1 요청 경로와 해소 경로 양쪽으로 평가한다

`ln -s ~/.ssh /tmp/x` 후 `/tmp/x/id_ed25519`를 읽는 것은 `~/.ssh/id_ed25519`를 읽는 것이며, 어휘 정규화만으로는 잡히지 않습니다.

따라서 정책은 **요청 경로와 해소 경로 둘 다에 대해 평가하고, 더 제한적인 결정을 채택합니다**. 제한 강도는 `forbid` > `deny` > `ask` > `allow` 순입니다.

두 경로를 모두 감사 엔트리에 기록합니다(`docs/audit-format.md` 6.3의 `file_access`). 불일치 자체가 우회 시도의 증거입니다.

### 4.2 TOCTOU

경로를 해소한 시점과 커널이 실제로 여는 시점 사이에 링크가 바뀔 수 있으며, 이는 경로 기반 중재의 구조적 한계입니다.

- Landlock은 경로가 아니라 inode에 규칙을 걸므로 이 문제를 겪지 않습니다. Linux 백엔드에서 실제 강제력이 나오는 이유입니다.
- seccomp user notification 기반 중재는 `notify_id_valid()` liveness 확인과 dirfd 기준 해석을 반드시 수행합니다.
- `observe` 백엔드는 강제하지 않으므로 TOCTOU가 보안 문제가 아니라 기록 정확도 문제입니다. 그래도 4.1의 양방향 평가는 수행합니다.

### 4.3 대소문자와 유니코드

macOS APFS는 기본적으로 대소문자를 구분하지 않습니다. 곧 `~/.SSH/id_rsa`가 `~/.ssh/id_rsa`와 같은 파일이며, 대소문자를 구분해 매칭하면 시크릿 deny 규칙이 통째로 우회됩니다.

동시에 대소문자를 항상 무시하면 `allow` 규칙이 의도보다 넓어집니다.

그래서 **제한 방향으로 갈리게** 정의합니다.

| 규칙의 action              | 매칭 방식                              | 근거                                     |
|-------------------------|------------------------------------|----------------------------------------|
| `forbid`, `deny`, `ask` | ASCII 대소문자 무시 + 유니코드 NFC 정규화 후 재비교 | 넓게 잡아야 안전. `.SSH`도, NFD 표기도 걸림         |
| `allow`                 | 바이트 그대로 비교                         | 좁게 잡아야 안전. `.Ssh`도 NFD 변형도 실수로 허용하지 않음 |

양쪽 모두 거부 쪽으로 실수합니다. 이것이 이 비대칭의 유일한 근거이며, 편의를 위한 예외를 두지 않습니다.

**유니코드 정규화.** APFS는 정규화를 구분하지 않으므로 NFC와 NFD로 표기된 같은 이름이 같은 파일을 가리킵니다. 바이트만 비교하면 `~/작업/*.pem` 같은 비ASCII `deny` 규칙을 NFD 표기 접근으로 우회할 수 있으므로, 제한 규칙은 바이트 비교가 빗나가면 양쪽을 NFC로 접어 한 번 더 비교합니다. ASCII 전용 세그먼트는 정규화가 항등이므로 추가 비용 없이 건너뜁니다.

비대칭은 대소문자와 같습니다. `allow`는 정규화를 넘나들며 넓어지지 않습니다. 정규화를 구분하는 볼륨(일부 네트워크 마운트)에서는 NFC와 NFD가 실제로 다른 파일이며, 그런 곳에서 `allow`가 양쪽에 걸리면 의도하지 않은 경로가 열리기 때문입니다.

**커널 계층.** macOS Seatbelt는 정규식 매칭 전에 경로를 자체 정규화하므로 프로파일 쪽은 원래 이 우회에 안전합니다(NFC/NFD 각 표기로 만든 파일과 각 표기의 접근 4가지 조합을 실측 확인). 그럼에도 제한 규칙은 프로파일에 두 형태를 모두 방출합니다. 커널 동작에 대한 가정을 하나 줄이는 값이 규칙 몇 줄보다 크기 때문이며, `allow` 규칙은 위와 같은 이유로 한 형태만 방출합니다.

## 5. glob 문법

패턴을 `/`로 나눈 세그먼트 열로 해석합니다.

| 토큰   | 의미                              |
|------|---------------------------------|
| `**` | 세그먼트 전체일 때만 유효. 0개 이상의 세그먼트에 매칭 |
| `*`  | 세그먼트 내 0개 이상의 바이트. `/`를 넘지 않음   |
| `?`  | 세그먼트 내 정확히 한 바이트. `/`를 넘지 않음    |

v1에 문자 클래스(`[abc]`)와 중괄호 확장(`{a,b}`)은 없습니다. 매처는 보안 경계이므로 표현력보다 검증 가능성을 택합니다.

매칭은 유니코드 문자가 아니라 **바이트** 단위로 수행합니다. 경로는 유닉스에서 임의의 바이트열이고 유효한 UTF-8이라는 보장이 없습니다. 문자열로 변환해 매칭하면 비UTF-8 경로가 손실 변환되면서 시크릿 규칙을 빗나갈 수 있으므로, `?`는 한 문자가 아니라 한 바이트에 매칭합니다. 비ASCII 이름에 `?`를 쓰는 것은 권장하지 않습니다.

`**`는 패턴당 최대 4개로 제한합니다. 중첩된 `**`는 백트래킹 비용이 세그먼트 수에 지수적으로 늘어날 수 있고, 경로는 신뢰할 수 없는 입력이기 때문입니다.

규칙은 다음과 같습니다.

- `a/**`는 `a` 자신과 그 아래 전부에 매칭합니다. 넓은 해석을 택하는 것이 deny 규칙에 안전합니다.
- `**`가 세그먼트의 일부로 나타나면(`a**b`) 로드 거부입니다. `*`로 오해될 소지를 없앱니다.
- 패턴은 확장 후 절대 경로여야 합니다. `/` 또는 `~/`로 시작하지 않으면 로드 거부이며, 단 `**/`로 시작하는 패턴과 `**` 단독은 "임의 위치"를 뜻하는 관용 표현으로 허용합니다(`**/.env*`).
- 매칭은 정규화된 경로에 대해 수행하며, 패턴 자체에는 `.`이나 `..`를 쓸 수 없습니다.

## 6. `file` 규칙

```toml
[[rules]]
kind = "file"
path = "~/.aws/**"
mode = ["read", "write", "create", "delete", "metadata", "exec"]
action = "deny"
```

`mode`를 생략하면 모든 모드에 적용됩니다. 생략이 넓은 쪽이므로 deny 규칙에 안전한 기본값입니다.

`path`에는 패턴 하나를 문자열로 쓰거나 여러 패턴을 배열로 쓸 수 있습니다. 배열은 같은 `id`와 같은 `mode`를 공유하는 패턴 묶음이며, 각 패턴은 5절 문법으로 따로 검증합니다.

```toml
path = ["~/.netrc", "~/_netrc"]
```

`read`와 `write`를 구분하는 것은 위협 모델상 의미가 있습니다. 시크릿 `read`는 반출이고 `write`는 지속성 확보이며, 다만 시크릿 경로에 대해서는 둘 다 막는 것이 기본입니다.

`metadata`는 `stat` 계열입니다. 존재 여부만으로도 정보가 새는 경우가 있으나 개발 도구가 광범위하게 사용하므로 기본 정책에서 `metadata`만 따로 막지 않습니다.

## 7. `exec` 규칙

```toml
[[rules]]
kind = "exec"
program = "rm"
argv_contains = ["-rf"]
argv_pattern = "*/dev/*"
action = "ask"
```

| 필드              | 의미                                                                                                      |
|-----------------|---------------------------------------------------------------------------------------------------------|
| `program`       | basename 또는 절대 경로. basename이면 어느 위치의 동명 프로그램에도 매칭. `/`를 포함하면 5절 glob으로 해석하므로 `/usr/bin/*` 같은 패턴도 쓸 수 있음 |
| `argv_contains` | 나열된 문자열이 argv에 **모두** 존재해야 매칭. 원소 단위 일치이며 부분 문자열 일치가 아님                                                 |
| `argv_pattern`  | argv를 `\x00`으로 이어붙인 문자열에 대한 glob                                                                        |

`program`과 `argv_contains`의 비교는 4.3절의 비대칭을 그대로 따릅니다. 곧 `forbid`/`deny`/`ask` 규칙은 ASCII 대소문자를 무시하고, `allow` 규칙은 바이트 그대로 비교합니다. `rm -RF`와 `SUDO`가 베이스라인 ask에 걸리는 이유이며, 양쪽 모두 거부 쪽으로 실수합니다.

### 7.1 exec 규칙의 한계를 분명히 한다

`exec` 규칙은 **보안 경계가 아니라 tripwire이자 UX 계층입니다.**

argv 수준 매칭은 원리적으로 우회 가능합니다. `sh -c 'r''m -rf /'`, base64 디코드 후 실행, 인터프리터 경유, 동적으로 조립한 인자 등 회피 경로가 무한합니다. argv 패턴을 촘촘히 쌓아 이를 막으려는 시도는 실패하며, 실패한다는 사실을 감춘 채 사용자에게 보호를 약속하는 것이 더 나쁩니다.

실제 방어는 두 곳에서 나옵니다.

- **자식 프로세스가 샌드박스를 상속합니다.** `rm -rf /`가 실행되어도 `file` 규칙이 허용하지 않은 경로는 지워지지 않으며, 파일 규칙이 진짜 경계입니다.
- **egress 규칙이 반출을 막습니다.** 어떤 명령으로 시크릿을 읽었든 내보낼 경로가 없습니다.

`exec` 규칙의 가치는 다릅니다. 명백히 위험한 의도를 사람에게 조기에 보여 주고(`ask`), 감사 로그에 굵은 흔적을 남기는 것이며, 그 역할로만 씁니다.

## 8. `egress` 규칙

```toml
[[rules]]
kind = "egress"
host = "*.githubusercontent.com"
port = 443
action = "allow"
```

- `host`는 도메인 패턴 또는 IP 리터럴입니다. `*.example.com`은 하위 도메인에 매칭하며 `example.com` 자신에는 매칭하지 않으므로, 둘 다 원하면 규칙을 둘 씁니다.
- `host = "*"`는 모든 호스트를 뜻하며 allowlist 정책의 마지막 차단 규칙으로 씁니다. `action = "allow"`와 함께 쓰면 로드 거부입니다. 아웃바운드 전면 허용은 `[defaults].egress = "allow"`와 실효가 같고, 2.2절이 문법 수준에서 막은 설정을 다른 문으로 세우는 것이기 때문입니다.
- `port`를 생략하면 모든 포트입니다.
- 매칭 전 호스트를 정규화합니다. 소문자화와 후행 점 제거까지만 수행합니다. 정규화 실패 시 매칭하지 않으며(=기본값으로 떨어짐) 기본값은 `allow`가 될 수 없습니다(2.2절).
- v1은 IDN을 punycode로 변환하지 않습니다. 비ASCII 호스트 패턴은 로드 거부이며, 국제화 도메인은 punycode(`xn--`) 형태로 직접 적습니다. IDNA 처리기를 TCB에 넣지 않기 위한 선택이며(`docs/design.md` 9.2), 관측된 호스트가 비ASCII면 정규화 실패로 처리되어 기본값으로 떨어집니다. 곧 특정 `deny` 규칙이 `[defaults].egress`보다 느슨해지지는 않습니다.
- 호스트명 없이 IP로 직접 연결하는 경우 `host`는 IP 문자열입니다. 도메인 패턴은 IP에 매칭되지 않습니다.
- IP는 canonical 형태로 정규화해 비교합니다. IPv4-mapped IPv6(`::ffff:1.2.3.4`)는 IPv4로 접어서 매칭하므로 표기 차이로 IP 단위 deny를 우회할 수 없습니다.

`docs/design.md` 10.1절 제약에 따라 호스트 단위 강제는 egress 프록시 층에서만 가능합니다. Landlock 백엔드는 포트 단위까지만 강제하며, 정책에 호스트 패턴이 있는데 프록시 층이 없으면 그 사실을 경고로 노출합니다. 강제되지 않는 규칙을 강제되는 것처럼 보이게 두지 않습니다.

## 9. 내장 베이스라인

`airlock-policy`에 컴파일되어 들어가며, 사용자 정책이 없어도 적용됩니다.

`forbid`로 두는 것은 다음과 같습니다(3.2절에 따라 명시적 `overrides`로만 완화 가능).

| id                   | 대상                                                                               | 근거                      |
|----------------------|----------------------------------------------------------------------------------|-------------------------|
| `ssh-private-keys`   | `~/.ssh/**`                                                                      | SSH 개인키와 known_hosts    |
| `aws-credentials`    | `~/.aws/**`                                                                      | 클라우드 자격증명               |
| `gcloud-credentials` | `~/.config/gcloud/**`                                                            | 클라우드 자격증명               |
| `kube-config`        | `~/.kube/**`                                                                     | 클러스터 관리자 자격증명           |
| `gpg-keyring`        | `~/.gnupg/**`                                                                    | 서명/복호화 키                |
| `env-files`          | `**/.env`, `**/.env.*`                                                           | 애플리케이션 시크릿              |
| `netrc`              | `~/.netrc`, `~/_netrc`                                                           | 평문 자격증명                 |
| `registry-tokens`    | `~/.npmrc`, `~/.pypirc`, `~/.cargo/credentials{,.toml}`, `~/.docker/config.json` | 패키지 레지스트리 토큰. 공급망 공격 경로 |
| `shell-history`      | `~/.bash_history`, `~/.zsh_history`, `~/.python_history`, `~/.psql_history` 등    | 과거 명령에 섞인 시크릿           |
| `system-credentials` | `/etc/shadow`, `/etc/sudoers`, `/etc/sudoers.d/**`                               | 시스템 자격증명                |
| `browser-profiles`   | Chrome/Chromium/Brave/Edge/Firefox/Safari 프로필과 쿠키 DB (macOS/Linux 경로)            | 세션 탈취                   |

`~/.ssh/**` 전체를 forbid로 두므로 `authorized_keys` 쓰기도 자동으로 덮입니다. 같은 대상을 약한 `ask` 규칙으로 다시 적는 것은 중복이고 갈라질 여지만 만듭니다.

`ask`로 두는 것은 다음과 같습니다.

| id                   | kind | 대상                                                                                                           |
|----------------------|------|--------------------------------------------------------------------------------------------------------------|
| `shell-init-write`   | file | `~/.bashrc`, `~/.bash_profile`, `~/.zshrc`, `~/.zshenv`, `~/.zprofile`, `~/.profile`, `~/.config/fish/**` 쓰기 |
| `git-config-write`   | file | `~/.gitconfig`, `~/.config/git/config` 쓰기. `core.pager` 등으로 코드 실행이 가능                                        |
| `autostart-write`    | file | `~/Library/LaunchAgents/**`, `~/.config/systemd/user/**`, `~/.config/autostart/**`, `/etc/cron.d/**` 쓰기      |
| `danger-rm`          | exec | `rm` + `-rf`                                                                                                 |
| `sudo-exec`          | exec | `sudo`                                                                                                       |
| `doas-exec`          | exec | `doas`                                                                                                       |
| `crontab-exec`       | exec | `crontab`                                                                                                    |
| `pipe-curl-to-shell` | exec | argv에 `curl ...                                                                                              | ...sh` 형태가 보임 |
| `pipe-wget-to-shell` | exec | argv에 `wget ...                                                                                              | ...sh` 형태가 보임 |

`shell-init-write`와 `autostart-write`, `crontab-exec`가 베이스라인에 있는 이유는, 위협 모델 3.2의 1번(프롬프트 인젝션)에서 공격자의 다음 수순이 거의 항상 지속성 확보이기 때문입니다. 한 번의 인젝션을 영구적 접근으로 바꾸는 경로를 기본으로 열어 두지 않습니다.

`forbid` 규칙은 전부 [3.3절의 probe](#33-무효한-완화-탐지)를 함께 정의합니다. probe 없는 `forbid`는 완화 침범을 검사할 수 없으므로 구현에서 테스트로 막습니다.

## 10. 로드 시 검증

로드는 아래를 모두 통과해야 성공합니다. 하나라도 실패하면 **정책이 적용되지 않고 실행이 중단됩니다.** 깨진 정책으로 실행을 계속하는 것은 fail-open이기 때문입니다.

1. `version`이 1입니다.
2. TOML 문법이 유효하고 알 수 없는 키가 없습니다.
3. `id`가 유일합니다. 사용자 규칙끼리 겹치지 않는 것은 물론이고 내장 베이스라인과 자기보호 규칙의 id와도 겹치지 않아야 합니다. 감사 로그의 `rule` 필드는 티어를 담지 않으므로, id가 겹치면 그 결정을 낸 규칙이 어느 티어의 것인지 로그만으로 알 수 없게 됩니다. `overrides`로 내장 id를 **지목**하는 것은 이와 별개이며 정상입니다.
3-1. `id`가 영숫자와 `.` `_` `-` `:` 로만 되어 있습니다. id는 macOS 커널 프로파일에 주석으로 그대로 들어가므로, 개행이 섞이면 주석이 거기서 끝나고 뒤 내용이 살아 있는 SBPL 지시문이 됩니다. 마지막 규칙이 이기는 언어라 그 자리에 넓은 `allow` 하나를 두면 베이스라인 forbid 까지 덮입니다. 강제 층도 방출 시점에 제어 문자를 한 번 더 지우지만, 로드 시점에서 먼저 막습니다.
4. 모든 `action`과 `kind`, `mode` 값이 알려진 값입니다.
5. 모든 `path` 패턴이 5절 문법에 맞고 절대 경로입니다.
6. `[defaults].egress`가 `allow`가 아닙니다.
7. `overrides`가 존재하는 내장 `forbid` id를 지목하고 `reason`이 비어 있지 않습니다.
8. `kind`에 맞지 않는 필드가 없습니다 (예: `file` 규칙에 `port`).

경고로만 보고하는 것은 다음과 같으며, 이 경우 로드는 성공합니다.

- 3.3절 probe 검사에서 발견된 무효한 완화 시도
- 앞선 규칙에 완전히 가려져 도달 불가능한 규칙
- 강제 백엔드가 표현할 수 없는 규칙 (8절의 호스트 패턴과 IP 리터럴 + 프록시 부재)
- 사용된 적 없는 `overrides`

뒤의 두 항목은 판정 기준을 고정합니다.

**도달 불가능 판정.** 3.3절과 같은 이유로 패턴 대수 대신 대표 경로를 씁니다. 규칙의 각 패턴에서 대표 경로를 하나씩 뽑고, 그 규칙이 가진 **모든** 패턴과 **모든** 모드의 조합을 앞선 규칙들이 빠짐없이 덮을 때만 경고합니다. 하나라도 덮이지 않으면 그 규칙은 도달 가능하므로 경고하지 않습니다. 하나만 덮여도 경고하면 좁은 규칙을 앞에 두고 넓은 규칙을 뒤에 두는 정상적인 정책이 전부 오탐이 되며, 조용히 무효한 규칙만큼이나 조용히 무시되는 경고도 나쁩니다.

**`overrides` 사용 여부 판정.** 그 규칙 자신이 닿는 범위가 지목한 `forbid` 규칙과 겹치는지로 판정합니다. `forbid`의 probe 경로로 판정하지 않는 이유는, [3.2절의 `read-ssh-config`](#32-forbid와-overrides) 예제처럼 probe를 비껴가면서도 실제로는 완화가 일어나는 정당한 규칙이 무효로 보고되기 때문입니다.

## 11. 정책 다이제스트

감사 로그 제네시스(genesis) 엔트리에 들어가는 값입니다(`docs/audit-format.md` 5.1).

```
policy_digest = SHA-256("airlock.policy.v1\x00" || canonical(정규화된 규칙 집합))
```

다이제스트는 원본 TOML 텍스트가 아니라 **정규화된 규칙 집합**에 대해 계산합니다. 주석과 공백, 키 순서가 바뀌어도 실효 정책이 같으면 같은 다이제스트가 나와야 합니다. 반대로 규칙 하나의 `action`, `path`, `reason`, 또는 규칙 **순서**가 바뀌면 반드시 달라지며, 순서가 3절에서 의미를 갖기 때문입니다.

정규화 인코딩은 [`docs/audit-format.md` 6.1](./audit-format.md#61-기본-요소)의 길이 접두 방식을 그대로 씁니다. 이 목적으로 `airlock-canonical` 크레이트를 감사 층과 공유합니다.

포함 대상과 표현 형태를 아래처럼 고정합니다. 목적은 다이제스트가 **머신에 종속되지 않게** 하는 것입니다. 같은 정책 파일이 다른 머신에서 다른 다이제스트를 내면 정책 비교와 배포 검증이 불가능해집니다.

| 대상           | 인코딩                                   |
|--------------|---------------------------------------|
| 티어 0 자기보호 규칙 | 구체 경로가 아니라 버전 표식 문자열 `selfprotect.v1` |
| `[defaults]` | 세 kind의 action 태그                     |
| 사용자 규칙       | 선언 순서대로 전부                            |
| 내장 베이스라인 규칙  | 정의 순서대로 전부                            |
| 경로 패턴        | **작성된 그대로**. `~`를 확장하지 않음             |

티어 0을 경로로 인코딩하지 않는 이유는 감사 디렉토리와 바이너리 경로가 설치마다 다르기 때문입니다. 대신 버전 표식을 넣어 자기보호 계약이 바뀌면 다이제스트도 바뀌게 합니다. 경로 패턴을 확장 전 형태로 인코딩하는 이유도 같으며, `~/.ssh/**`는 어느 머신에서든 같은 규칙입니다.

## 12. `airlock policy explain`

1절의 결정 가능성을 사용자에게 노출하는 명령입니다.

```bash
$ airlock policy explain --file ~/.ssh/config --mode read
# 요청     /Users/me/.ssh/config
# 해소     /Users/me/.ssh/config
# 모드     read
# 결정     forbid
# 규칙     ssh-private-keys (baseline tier)
# 매칭     ~/.ssh/**
# 근거     SSH 개인키와 known_hosts
```

무엇이 왜 막혔는지 즉시 답하지 못하는 정책 엔진은 false positive 튜닝이 불가능하고, 곧 `docs/design.md` 8장의 "개발자 짜증" 리스크를 방치하게 됩니다.

## 13. 테스트 의무

### 평가 의미론

- 티어 0 규칙이 사용자 `allow`보다 우선함
- 티어 0 규칙은 `overrides`로도 뚫리지 않음
- 사용자 규칙 선언 순서대로 첫 매칭이 이김
- 매칭 없으면 `[defaults]`로 떨어짐
- `ask` 응답 없음과 tty 부재가 모두 거부로 귀결됨

### 로드 검증

- [9절](#9-내장-베이스라인)의 모든 `forbid` probe에 대해, `overrides` 없는 사용자 `allow`는 실제 결정을 바꾸지 못하고 경고만 냄
- 넓은 작업 공간 `allow` 규칙이 그 안의 `.env`와 `~/.ssh`를 열지 못함 ([3.0절](#30-왜-forbid가-사용자-규칙보다-위인가))
- `overrides`가 있고 `reason`이 빈 문자열이면 로드 실패
- 알 수 없는 키, 오타 난 `action`, 상대 경로 패턴, `a**b` 패턴이 각각 로드 실패
- `[defaults].egress = "allow"`가 로드 실패
- `[defaults]`의 세 kind 어디든 `forbid`면 로드 실패 ([2.2절](#22-defaults))
- 사용자 규칙의 `action = "forbid"`가 로드 실패 ([2.1절](#21-공통-필드))
- 겹치는 `forbid` 중 하나만 `overrides`로 지목했을 때, 지목하지 않은 나머지는 계속 이김 ([3.2절](#32-forbid와-overrides))

### 경로 정규화 (적대적)

각 항목은 시크릿에 도달하려는 실제 우회 시도이며, 전부 `deny`가 나와야 합니다.

- `~/.ssh/../.ssh/id_rsa`
- `~/work/../.ssh/id_rsa`
- `/Users/me/./.ssh//id_rsa`
- `~/.ssh/./id_rsa`
- `/tmp/link -> ~/.ssh` 후 `/tmp/link/id_rsa`
- `/tmp/a/b` 중 `a`가 `~/.ssh`로의 링크인 중간 세그먼트 링크
- `~/.SSH/id_rsa`, `~/.Ssh/id_rsa` ([4.3절](#43-대소문자와-유니코드) 대소문자)
- `~/작업/*.pem`이 `deny`일 때 NFD로 표기한 `~/작업/키.pem` ([4.3절](#43-대소문자와-유니코드) 정규화)
- `link -> ~/.ssh` 후 `link/../.ssh/id_rsa` (커널은 링크를 먼저 따르고 `..`를 나중에 적용)
- 루트 위로 올라가는 `../../../../etc/shadow`
- 존재하지 않는 경로를 포함한 `~/.ssh/nonexistent/../id_rsa`

반대 방향으로, `allow` 규칙이 대소문자나 정규화 변형으로 넓어지지 않는지 확인합니다.

- `~/work/proj/**`가 `allow`일 때 `~/WORK/proj/x`는 `allow`가 아님
- `~/작업/**`가 `allow`일 때 NFD로 표기한 `~/작업/x`는 `allow`가 아님

### glob 매처

- `*`가 `/`를 넘지 않음
- `**`가 0개 세그먼트에 매칭 (`a/**`가 `a`에 매칭)
- `**/.env*`가 임의 깊이의 `.env`, `.env.local`에 매칭
- `?`가 정확히 한 문자이며 `/`를 넘지 않음

### egress

- `*.example.com`이 `a.example.com`에 매칭하고 `example.com`에는 매칭하지 않음
- `EXAMPLE.com.`이 `example.com`으로 정규화됨
- 도메인 패턴이 IP 리터럴에 매칭하지 않음
- 비ASCII 호스트 패턴이 로드 거부됨
- IPv4-mapped IPv6(`::ffff:1.2.3.4`)이 IPv4로 접혀 IP 단위 deny를 우회하지 못함

### 다이제스트

- 주석과 공백, 규칙 필드 순서만 다른 두 정책의 다이제스트가 같음
- `action` 하나만 다른 두 정책의 다이제스트가 다름
- 규칙 순서가 다르면 다이제스트가 다름 (순서가 의미를 바꾸므로)
